# IT 解决方案知识库

> 使用说明：本库按《完整的 IT 解决方案分层》组织，覆盖从战略到基础设施的七层规范、架构方案标准、服务器操作系统与部署、安全合规与攻防防御、界面设计规范。
> 第一篇用于方案设计与评审：先定业务边界，再逐层检查划分标准、设计规则、算法选型与验收指标。
> 第二篇用于服务器与服务的部署、调优、上线基线；第三篇用于安全建设、等保合规、攻防防御与上线前安全检查。
> 第四篇用于界面设计：先明确用户目标与心智模型，再按人因、心理、美学与各应用场景规范执行并走查。
> 各篇条目均为可执行检查项；标注“必须”的条目属于质量或合规门禁，参数为起始参考，需按实测与业务约束校准。
> 已剔除过时做法（旧等保表述、Flash、MapReduce 为主等），并融合当前通行的云原生、零信任、WCAG 2.2、设计系统等标准。

## 第一篇 解决方案分层规范与架构标准

### 第1章 战略与业务层
#### 1.1 定义、组成与划分标准
- **定义**：战略与业务层规定组织为什么投入、为哪些利益相关者创造什么价值，以及如何用可验证的业务结果衡量价值。
- **组成单位**：战略目标、利益相关者、业务能力、价值流、业务流程、业务规则、政策约束、OKR、KPI、需求与投资组合。
- **划分标准**：以业务边界和价值归属划分，不以部门汇报线、产品界面或技术平台划分；替换全部技术实现后，能力与规则仍有意义。
- **制品基线**：业务能力地图、价值流图、业务术语表、业务规则目录、需求优先级清单、收益假设、风险登记册、OKR/KPI 树。
- **追踪关系**：每个需求必须关联“战略目标 → 业务能力 → 价值流阶段 → 衡量指标 → 负责人”，无关联项不进入交付计划。
#### 1.2 设计规则（高效、简洁、安全、合理）

| 维度 | 强制规则 |
| --- | --- |
| 高效 | 先识别价值流瓶颈与等待时间，再决定是否建设系统；优先自动化高频、高耗时、高错误率且规则稳定的环节。 |
| 简洁 | 能力名称使用业务动宾结构或稳定名词；同一概念只保留一个定义、一个业务负责人和一个权威数据源。 |
| 安全 | 在立项时完成数据分级、合规义务、业务连续性、欺诈与滥用风险评估；高风险假设须设置止损条件。 |
| 合理 | 将探索性需求与确定性需求分开管理；以结果指标而非功能数量评价交付，以约束指标防止局部优化。 |

- **能力地图**：一级能力对应稳定业务域，二级能力对应可独立评估成熟度与投资的能力；不得把“微服务、数据库、网关”列为业务能力。
- **价值流**：从利益相关者触发到价值实现为止，记录每阶段处理时间、等待时间、移交、返工率、自动化率与责任角色。
- **OKR 拆解**：目标描述方向性改变；每个目标配置 2～5 个具有基线、目标值、期限和数据源的关键结果，KR 不得写成任务清单。
- **KPI 拆解**：结果指标必须配对质量、风险或成本护栏，例如“订单转化率”同时观察“退款率、欺诈损失率、履约成本”。
- **需求准入**：问题、目标人群、现状基线、预期收益、约束、验收证据、负责人缺一不可；缺少基线的收益承诺只作为假设。
- **变更治理**：新增范围必须说明被替换的同级事项及其机会成本；监管红线和安全底线不得用交付进度抵消。
#### 1.3 常用算法或模式

| 方法 | 计算或执行规则 | 适用场景与限制 |
| --- | --- | --- |
| WSJF | `优先级 = 延迟成本 / 工作时长`；延迟成本综合用户价值、时间敏感性和风险降低，各项使用同一相对尺度 | 用于同一投资组合内排序；估算粒度过大或缺少共同尺度时不可机械比较 |
| RICE | `RICE = Reach × Impact × Confidence / Effort`；触达量与投入必须采用同一时间窗口，信心度取 0～1 | 适合产品需求；不能替代合规、韧性和技术债的强制投入 |
| 加权评分 | `得分 = Σ(指标权重 × 标准化得分)`；权重和原始分均留痕，并做敏感性分析 | 适合多约束决策；不得用相加掩盖“一票否决”的风险项 |
| 价值流分析 | `流动效率 = 增值处理时间 / 端到端前置时间`；同时统计等待、移交和返工 | 用于定位系统性瓶颈，不用于评价个人产出 |
| 成本延迟分析 | 估算单位时间未交付造成的损失，并区分固定、递增、阶梯式到期损失 | 适合有明确时间窗口的需求；无法货币化时可采用相对等级 |
| MoSCoW | Must 必须给出不交付即失败或违规的证据；Should/Could/Won't 在每次规划期重审 | 适合范围协商；不得把绝大多数需求都列为 Must |
| 假设驱动交付 | 建立“假设—实验—样本—阈值—期限—停止条件”，先验证最大不确定性 | 适合创新需求；探索实验不得绕过隐私和生产安全约束 |
#### 1.4 度量指标与验收标准

| 指标 | 计算与验收规则 |
| --- | --- |
| 战略覆盖率 | 已立项需求中能完整追溯到战略目标的比例必须为 100%，孤立需求须撤销或补充决策。 |
| 指标可核验率 | OKR/KPI 具有基线、目标、期限、负责人和自动数据源的比例为 100%。 |
| 流动效率 | 按价值流持续观测；优化方案必须同时给出处理时间和等待时间的变化，禁止只压缩局部处理时间。 |
| 预测可靠性 | 比较预测收益与实际收益，按季度复盘偏差；连续失准的组合必须重校准估算方法。 |
| 需求吞吐与老化 | 同时观察交付周期、在制品数量、积压年龄；超过有效期的需求重新验证，不自动延期。 |
| 护栏合规率 | 合规、隐私、安全和连续性红线验收通过率必须为 100%，不得以平均收益冲抵。 |

- **验收门禁**：业务、产品、财务或数据负责人共同确认收益口径；上线后按预设窗口复核收益，不达标项进入调整或退出流程。
- **反伪造规则**：不得仅以上线日期、需求数量、故事点或加班时长作为业务成功证据。
#### 1.5 反模式清单

- 以技术采购或“建设大中台”为起点，反向寻找业务价值。
- 将组织架构直接复制为能力地图，导致跨部门价值流无人负责。
- OKR 全是任务、KPI 无基线，或通过压低基线制造达成率。
- 用精确小数包装主观评分，不保留权重、假设和敏感性分析。
- 所有需求均为最高优先级，在制品不受限，长期积压项从不退出。
- 只衡量收入增长，忽略退款、风险、债务、运维成本与客户伤害。
### 第2章 应用/解决方案层
#### 2.1 定义、组成与划分标准

- **定义**：应用/解决方案层规定用哪些应用、服务和集成关系承载业务能力，并明确它们对外的契约与运行责任。
- **组成单位**：应用系统、微服务、限界上下文、API、事件、数据产品、集成适配器、服务治理策略。
- **划分标准**：以业务领域、数据所有权、变化原因和独立交付边界划分；禁止按“控制器服务、逻辑服务、数据库服务”等技术职能横向拆服务。
- **制品基线**：上下文地图、服务目录、API/事件契约、数据所有权矩阵、依赖图、SLO、部署拓扑、架构决策记录（ADR）。
#### 2.2 领域与服务边界设计规则

| 维度 | 强制规则 |
| --- | --- |
| 高效 | 让高变更、高扩展或高独立可用性需求的能力独立交付；低变化且强一致的小域优先保持模块化单体。 |
| 简洁 | 一个限界上下文内使用统一语言，同一术语在不同上下文允许不同模型，不为追求“企业统一模型”制造巨型对象。 |
| 安全 | 每个服务明确数据所有者、访问主体、信任边界和最小权限；跨信任域通过显式契约与防腐层转换。 |
| 合理 | 服务边界必须能由一个小团队理解、测试、发布和值守，且与业务变化频率、事务边界、扩展特征相匹配。 |

- **限界上下文判据**：统一语言、模型不变量、数据所有权和业务规则在同一边界内保持一致；出现同词异义时先澄清模型，而非加类型字段。
- **上下文关系**：共享内核仅限双方共同维护的小模型；客户/供应方明确契约协商；开放主机服务提供稳定公共协议；防腐层隔离外部模型。
- **微服务拆出必要条件**：存在独立部署、独立扩缩容、故障隔离、数据主权或合规隔离中的至少一项明确收益，并具备自动测试、持续交付和可观测能力。
- **保留单体判据**：团队规模小、域边界仍不稳定、跨域操作频繁强一致、运维能力不足或网络成本高于收益时，先实施模块化单体。
- **数据规则**：服务私有数据不得被其他服务直接写库；跨服务读取通过 API、事件副本或数据产品，副本必须标记来源、时效和一致性。
- **服务治理**：统一服务身份、注册发现、配置、密钥、流量策略、契约测试、SLO 和退役流程；服务网格仅在多语言、规模或治理收益明确时采用。
#### 2.3 API 与事件设计规范

- **资源建模**：REST 路径使用名词和层级资源，动作无法资源化时才使用 `actions` 子资源；查询、排序、过滤字段采用白名单。
- **版本策略**：全系统选择路径版本或请求头版本之一；默认向后兼容，破坏性变更才升主版本，并公布弃用期、迁移指南和下线日期。
- **兼容规则**：新增可选字段通常兼容；删除字段、收窄枚举、改变类型、改变默认语义、复用错误码含义均属于破坏性变更。
- **幂等规则**：创建、支付、退款等非天然幂等操作必须支持幂等键；键按“调用方＋操作＋业务作用域”隔离，保存期覆盖最大重试及异步结算窗口。
- **幂等实现**：首次请求持久化“键＋请求摘要＋处理状态＋结果”；同键同摘要重放返回原结果，同键不同摘要返回冲突，不得重复扣款或建单。
- **分页规则**：大且变化频繁的数据使用游标分页，游标包含稳定排序键和方向并签名或做不透明编码；限制页大小，默认与最大值写入契约。
- **排序规则**：排序键必须确定且包含唯一决胜字段；禁止以无序集合配合偏移分页作为实时大列表的长期方案。
- **错误响应**：统一返回机器可读 `code`、人可读 `message`、可选 `details` 和 `requestId`；不得泄露堆栈、SQL、内部主机或敏感数据。

| HTTP 状态 | 使用规则 |
| --- | --- |
| 400 / 422 | 400 表示格式或协议错误；422 表示语法正确但业务语义不可处理，字段错误须可定位。 |
| 401 / 403 | 401 表示未认证或凭证失效；403 表示已认证但无权执行，禁止混淆。 |
| 404 / 409 | 404 表示资源不存在或按防枚举策略不可见；409 表示版本、状态或幂等键冲突。 |
| 429 | 表示触发限流，按协议提供 `Retry-After`，并说明限流维度。 |
| 500 / 502 / 503 / 504 | 分别表示内部错误、上游无效响应、暂时不可用、上游超时；仅临时错误建议重试。 |

- **事件契约**：事件包含唯一 ID、类型、版本、发生时间、生产者、追踪 ID、主体 ID 和负载；采用“至少一次”投递时消费者必须去重。
- **事件语义**：区分业务事实与命令，不在事件名中含糊表达；事件演进优先增加可选字段， schema 注册表执行兼容性检查。
#### 2.4 常用模式、度量与验收

| 模式 | 规则 |
| --- | --- |
| API 网关 | 负责边缘认证、路由、配额和协议终止；业务规则必须回到领域服务，避免“网关即逻辑中心”。 |
| BFF | 面向特定客户端聚合视图，不拥有核心领域数据；多个 BFF 不得复制同一业务规则。 |
| 防腐层 | 在边界完成模型、错误、单位和语义转换；禁止外部字段穿透内部模型。 |
| 侧车/服务网格 | 统一传输安全与流量治理，但不能替代应用级授权、幂等和业务监控。 |
| Strangler Fig | 以可验证业务切片逐步迁移，新旧系统按明确路由和数据所有权共存，完成后删除旧路径。 |

- **验收指标**：服务均有负责人、SLO、依赖图和运行手册；公开 API 契约测试通过率 100%，破坏性变更检测通过率 100%。
- **运行指标**：按服务观察请求率、错误率、P95/P99/P99.9 延迟、饱和度、依赖错误预算和变更失败率，不以平均延迟验收。
- **边界指标**：统计跨服务同步调用跳数、分布式事务数、共享表数和循环依赖数；关键请求同步链应尽可能短且每跳均有预算。
- **恢复验收**：幂等重放、重复事件、乱序事件、限流、上游超时、版本兼容和退役流程必须有自动化测试证据。
#### 2.5 反模式清单

- 按每个实体或每张表建立一个微服务，形成大量“CRUD 纳米服务”。
- 多服务共享数据库并可相互写表，以服务名称伪装分布式单体。
- 所有服务同步级联，一个非核心依赖故障导致全链路不可用。
- 在网关、消息中间件或存储过程中堆积核心业务规则。
- 以 URL 加版本号代替兼容治理，旧版本永久保留且无消费者清单。
- 把“消息已入队”误当成端到端成功，或宣称消息系统天然恰好一次。
### 第3章 程序/模块层
#### 3.1 定义、组成与划分标准

- **定义**：程序/模块层规定单个应用内部的代码组织、依赖方向和构建边界，使变化原因相同的代码共同演进。
- **组成单位**：模块、组件、包、命名空间、构建产物、端口、适配器、公共契约和内部实现。
- **划分标准**：以业务子域、变化原因、复用边界和依赖稳定性划分，兼顾高内聚、低耦合和独立可测试性。
- **制品基线**：模块图、允许依赖清单、公共 API 清单、构建依赖图、模块负责人、架构适应度函数。
#### 3.2 设计规则（高效、简洁、安全、合理）

| 维度 | 强制规则 |
| --- | --- |
| 高效 | 将高频一起变化的代码放在同一模块；通过编译边界和接口隔离缩短增量构建与测试范围。 |
| 简洁 | 公共接口只暴露完成用例所需操作；模块内部实现默认私有，禁止以“以后可能复用”为由提前抽象。 |
| 安全 | 领域核心不得导入 Web、ORM、消息或 UI 框架；跨边界数据必须校验，模块权限与凭据按最小范围配置。 |
| 合理 | 模块按业务能力和稳定抽象划分，不追求所有模块同尺寸；拆分必须降低认知、变更或运行成本中的至少一项。 |

- **依赖方向**：外层依赖内层，接口、应用和领域策略不依赖基础设施实现；由组合根完成依赖装配。
- **无环依赖**：模块与包依赖图必须是有向无环图；发现环路时优先提取真正公共概念或反转依赖，不新建“万能 common”。
- **稳定依赖**：易变模块可以依赖稳定模块，稳定核心不得依赖易变细节；抽象不应机械追求，领域实体可以保持具体。
- **信息隐藏**：数据结构、校验规则、事务和第三方差异由所属模块封装；调用方不得依赖实现私有表结构或异常类型。
- **分层架构**：接口层处理协议，应用层编排用例与事务，领域层保护业务不变量，基础设施层实现外部资源访问。
- **六边形架构**：端口表达应用需求或对外能力，适配器处理技术细节；只有存在替换、隔离测试或多入口价值时才设置端口。
- **模块复用**：复用发布物必须版本化并有独立契约；严禁通过相对路径深入其他模块内部复用私有实现。
#### 3.3 常用模式与度量

| 模式或指标 | 规则与判据 |
| --- | --- |
| Facade | 为复杂子系统提供单一用例入口，不把所有模块调用转发成无价值透传层。 |
| Adapter | 将外部协议转换为内部端口；适配器可替换，领域模型不感知外部类型。 |
| Dependency Injection | 在组合根注入依赖；业务代码不得自行定位全局服务或读取环境单例。 |
| Plugin | 针对确有多个实现且变化点稳定的能力使用，插件接口版本化并限制权限。 |
| LCOM4 | 统计类内“方法—字段”连通分量；大于 1 提示可能多职责，但需结合语义审查，不机械拆类。 |
| 传入/传出耦合 | `Ca` 为传入依赖，`Ce` 为传出依赖；分别评估被改影响与外部变化暴露，不单看总数排名。 |
| 不稳定性 | `I = Ce / (Ca + Ce)`，范围 0～1；用于观察依赖稳定性，不规定所有模块必须趋近某端。 |
| 抽象度与主序列距离 | `A = 抽象类型数 / 总类型数`，`D = |A + I - 1|`；仅作趋势信号，不能替代领域判断。 |
#### 3.4 模块拆分检查表与验收标准

- [ ] 模块名称能否用业务语言说明其职责，而非 `util`、`manager`、`base` 等泛称？
- [ ] 模块是否只有一个主要变化原因，并能给出最近三次变更的归属证据？
- [ ] 是否能仅依赖公开接口构建和测试，而不读取其他模块私有实现？
- [ ] 是否不存在循环依赖、跨层调用、共享可变全局状态和隐式启动顺序？
- [ ] 是否明确数据、事务、配置、错误和日志的归属？
- [ ] 删除某个实现后，是否只需替换适配器而不修改领域规则？
- [ ] 拆分后是否实际减少构建、测试、发布或认知成本，而非增加转发代码？

- **验收门禁**：依赖循环为 0，领域层对框架依赖为 0，未声明跨模块引用为 0，公共 API 变更均通过兼容性检查。
- **质量趋势**：持续跟踪模块大小、Ca/Ce、共同变更新率、构建时间、缺陷密度和变更失败率；阈值按仓库基线设定并防止逐季恶化。
- **变更验收**：一次常规业务变更不应无理由穿透全部技术层；若必须穿透，需说明是契约变化还是模块边界失效。
#### 3.5 反模式清单

- 以 `common/utils` 汇集无共同变化的代码，最终所有模块都依赖它。
- 每个接口只有一个实现且永远无替换价值，却仍叠加工厂、 Builder、Facade 和代理。
- 领域对象直接序列化为 API 或数据库记录，导致任一外部变化穿透核心。
- 按技术层建包后跨实体复制同名 DTO，形成大量无语义转换代码。
- 用依赖注入容器隐藏循环依赖和服务定位，组合根失去可审计性。
- 为追求指标把内聚类拆碎，或为了“主序列距离”给所有实体创建接口。
### 第4章 单元/函数层
#### 4.1 定义、组成与划分标准

- **定义**：单元/函数层将用例和业务不变量封装为可独立理解、调用和验证的类、函数、方法或对象。
- **组成单位**：类、接口、函数、方法、闭包、实体、值对象、领域服务、测试单元。
- **划分标准**：以单一职责、行为内聚、可替换性和测试独立性划分；函数边界对应一个完整意图，而非任意行数。
- **制品基线**：公开签名、前置/后置条件、不变量、错误契约、复杂度记录、单元与属性测试。
#### 4.2 SOLID 与函数设计规则

| 原则 | 可执行规则 |
| --- | --- |
| SRP 单一职责 | 一个单元只因一类角色或业务规则变化而修改；持久化、协议与领域计算无必要时不得混在同一单元。 |
| OCP 开放封闭 | 对已稳定的扩展点使用策略或多态；无实际变化征兆时不预埋抽象。 |
| LSP 里氏替换 | 子类型必须满足父类型的前置条件、后置条件和不变量；不得通过抛“不支持”异常缩小契约。 |
| ISP 接口隔离 | 按调用方需要定义小接口，禁止强迫客户端依赖其不使用的方法。 |
| DIP 依赖倒置 | 高层策略依赖其拥有的抽象，外部实现依赖该抽象；避免业务代码直接实例化外部资源。 |

| 维度 | 默认规则 |
| --- | --- |
| 高效 | 优先清晰的数据流与批量边界；避免在循环中重复查询、重复解析和创建无意义临时对象。 |
| 简洁 | 函数做一件命名可表达的事；默认不超过 30 行可执行代码、3 层嵌套、3 个位置参数，超限须审查而非自动拆分。 |
| 安全 | 在信任边界校验输入；内部使用类型、不变量和构造器阻止非法状态，不能依赖层层重复判空。 |
| 合理 | 查询尽量无副作用，命令的写入、外部调用和事务边界显式可见；不机械执行绝对命令查询分离。 |

- **参数规则**：多个同属一个概念且稳定成组出现的参数封装为参数对象；禁止用布尔参数切换两条无关流程。
- **返回值规则**：返回领域含义完整的结果，不通过可变入参秘密回传；部分成功必须返回逐项结果，不能只返回整体成功。
- **副作用规则**：时间、随机数、网络、磁盘和全局状态通过显式依赖或输入注入，使核心计算可重复验证。
- **命名规则**：类使用领域角色，函数使用准确动词，布尔使用可判断的谓词；单位、时区和精度写入名称或类型。
- **注释规则**：解释为什么、约束、权衡和非显然协议，不复述代码；公开契约、正则、位运算和并发假设必须有可验证说明。
- **错误规则**：可恢复业务失败使用明确结果或领域异常，程序缺陷快速失败；不得空捕获、把异常当日志或重复包装丢失原因。
#### 4.3 常用模式、测试与度量

- **常用模式**：值对象、领域服务、策略、规格、模板方法、组合、装饰器、工厂；只有在降低变化成本时采用。
- **实体与值对象**：实体按身份区分并控制生命周期；值对象按值相等且优先不可变，可安全共享或整体替换。
- **测试结构**：采用 Arrange-Act-Assert 或 Given-When-Then，每个测试验证一个行为，名称说明条件与预期。
- **边界用例**：至少覆盖空、单元素、最小/最大值、越界、重复、乱序、非法状态、精度、时区、Unicode、溢出和外部失败中的适用项。
- **测试替身**：只模拟拥有的外部端口，优先真实领域对象；不得模拟第三方全部行为后把假设当事实，关键集成须用契约测试。
- **属性测试**：对序列化往返、排序、金额、不变量和状态机采用生成式输入，并保存最小反例。

| 指标 | 默认验收门槛 |
| --- | --- |
| 圈复杂度 | 单函数通常不超过 10；超过时须拆分或用决策表验证全部关键路径。 |
| 行/分支覆盖率 | 存量核心代码行覆盖率不低于 80%、分支不低于 70%；新增或修改行覆盖率不低于 90%。 |
| 关键不变量 | 金额、权限、库存、状态迁移等关键规则的正常与拒绝路径覆盖率为 100%。 |
| 测试有效性 | 变异测试用于核心模块抽检；覆盖率提升必须伴随有效断言，禁止无断言调用凑数。 |
| 测试稳定性 | 非确定性测试为 0；固定时钟、随机种子和网络替身，失败可重复且能定位单一原因。 |
#### 4.4 反模式清单

- 函数名称为 `process` 或 `handle`，同时解析、校验、计算、写库、发消息和组装响应。
- 为了缩短行数拆出大量只有一行、名称模糊且必须跳转阅读的函数。
- 以布尔、空值或魔法数表示多个隐藏状态，以输出参数回传结果。
- 继承复用导致子类违反父类契约，或父类测试需知道每个子类特例。
- 测试只覆盖 mock 调用次数，不断言业务结果；修改实现但不改行为时测试大面积失效。
- 注释复述语法、保留过期代码块，或用注释解释本可通过命名消除的歧义。
### 第5章 算法/逻辑层
#### 5.1 定义、组成与划分标准

- **定义**：算法/逻辑层用明确的数据结构、计算规则和状态转换，在给定资源与正确性约束下完成数据处理。
- **组成单位**：数据结构、算法流程、纯函数、业务规则、决策表、状态机、不变量、概率结构和并发协调协议。
- **划分标准**：按问题模型与输入输出契约划分；核心逻辑不夹杂 UI、网络或存储 I/O，外部数据经适配后进入计算。
- **分析基线**：必须记录输入规模、分布、时间/空间复杂度、最坏情况、摊还条件、精度、资源上界和失败语义。
#### 5.2 复杂度与逻辑设计规则

| 维度 | 强制规则 |
| --- | --- |
| 高效 | 同时分析平均、最坏、摊还时间与额外空间；结合常数、缓存局部性、分配次数和实际数据分布选型。 |
| 简洁 | 优先成熟标准库与已知数据结构，只有剖析证据证明瓶颈后才实现自定义算法或位级优化。 |
| 安全 | 明确整数溢出、浮点误差、哈希碰撞、对抗性输入、随机数质量和概率误差；不可接受误判时不得使用近似结构。 |
| 合理 | 以正确性不变量和终止条件约束实现；任何性能优化必须保持等价测试，并用基准数据证明净收益。 |

- **复杂度表达**：写明 `n` 的含义，分别给出预处理、单次操作和全量任务复杂度；递归需分析栈深，外部存储需分析 I/O 次数。
- **纯函数**：相同输入产生相同输出，不读取或修改隐藏状态；需要时间、熵或外部数据时作为显式输入。
- **状态机**：列出状态、事件、守卫、动作和迁移；非法迁移显式拒绝，终止状态不可被普通事件重新进入。
- **决策表**：多条件组合使用完备且互斥的规则表；标明默认分支和优先级，防止规则重叠产生不可预测结果。
- **数值规则**：金额使用十进制或最小货币单位整数，定义舍入模式；近似计算给出误差上界，不用浮点直接比较金额相等。
#### 5.3 常用算法选型表

| 问题 | 首选算法或结构 | 复杂度与选择条件 |
| --- | --- | --- |
| 小规模排序 | 插入排序 | 平均/最坏 `O(n²)`、空间 `O(1)`；近有序或很小数组有低常数优势。 |
| 通用排序 | 内省排序；需稳定时采用归并/Tim 类排序 | 通常 `O(n log n)`；必须确认稳定性、最坏情况和额外空间，不自行实现快速排序。 |
| 外部排序 | 分块排序＋k 路归并 | 数据超过内存时使用；核心指标为顺序 I/O、归并趟数和临时空间。 |
| 精确查找 | 哈希表或平衡搜索树 | 哈希平均 `O(1)`、最坏可退化；有序范围查询用树 `O(log n)`。 |
| 有序数组查找 | 二分查找 | `O(log n)`；输入必须按相同比较规则有序，并检查中点与边界计算。 |
| Top K / 调度 | 二叉堆或优先队列 | 建堆 `O(n)`，取顶/插入通常 `O(log n)`；全排序不是 Top K 的默认方案。 |
| 图最短路 | BFS、Dijkstra、A* 或 Bellman-Ford | 无权图用 BFS；非负权用 Dijkstra/A*；负权用 Bellman-Ford 并检测负环。 |
| 连通与动态分组 | 并查集 | 路径压缩＋按秩/大小合并，摊还接近 `O(1)`；不直接支持任意删除。 |
| 缓存淘汰 | LRU、LFU 或 W-TinyLFU | LRU 适合近期局部性；扫描型负载和长期热点优先准入策略与频率估计。 |
| 限流 | 令牌桶、漏桶、滑动窗口 | 令牌桶允许受控突发；漏桶平滑输出；固定窗口仅在可接受边界突增时使用。 |
| 分布式缓存路由 | 一致性哈希＋虚拟节点 | 节点变化仅迁移部分键；监控倾斜，不用普通 `hash(key) mod N` 应对频繁扩缩容。 |
| 大规模成员预筛 | 布隆过滤器 | 无误漏判、有误判；标准版不可删除，误判率上升前扩容重建。 |
| 短临界区互斥 | 数据库条件更新或带租约锁＋ fencing token | 优先利用存储原子性；锁必须验证持有者、过期与 fencing，不能据此宣称恰好一次。 |
| 复制元数据共识 | Raft 或 Paxos 类协议 | 用于选主和复制日志等强一致元数据；业务服务优先复用成熟系统而非自研。 |
#### 5.4 概率结构与分布式算法约束

- **布隆过滤器容量**：给定预期元素数 `n` 和误判率 `p`，位数 `m = -n ln p / (ln 2)²`，哈希数 `k = (m/n) ln 2`；必须按实际插入量复算。
- **限流一致性**：单实例内存算法不能直接代表集群全局限额；全局限额需共享状态或明确的分片配额，并允许定义误差窗口。
- **锁的正确性**：锁服务不可用时定义 fail-open 或 fail-closed；资金、库存等关键写默认 fail-closed，并以条件更新保护最终不变量。
- **共识与法定人数**：多数派写入和读取只有在满足协议、成员与故障假设时才提供对应一致性；`W + R > N` 不是脱离协议语义的万能证明。
- **重试与算法**：任何分布式协调算法都必须给出超时、重复、乱序、时钟回拨和节点重启后的行为。
#### 5.5 度量指标与验收标准

- **正确性**：提供不变量证明或反例驱动测试；与简单参考实现对拍，属性测试覆盖随机、极端和大规模输入。
- **性能**：基准测试包含预热、多轮样本、P50/P95/P99、吞吐、分配量和内存峰值，并固定数据分布、运行环境和编译参数。
- **上界**：除渐近复杂度外给出可接受的最大输入、最大耗时、最大内存和降级策略；无法终止的递归或循环不得进入生产。
- **概率误差**：布隆过滤器、HyperLogLog、Count-Min Sketch 等必须公布目标误判/误差、容量假设和超限行为。
- **验收门禁**：核心算法必须有复杂度记录、基准报告、边界测试和回退实现；优化前后结果等价且性能提升超过测量噪声。
#### 5.6 反模式清单

- 只写平均 `O(1)` 而忽略碰撞、扩容、对抗输入与最坏情况。
- 为微小数据自研复杂结构，或未经剖析使用位运算、缓存池和无锁结构。
- 使用布隆过滤器做授权、余额等不容误判的最终判断。
- 在集群每实例独立限流却宣称全局限额，或依赖本机时钟保证跨节点严格顺序。
- 用 Redis 锁替代数据库不变量，锁过期后直接续租而无持有者身份和 fencing。
- 自研 Paxos/Raft、分布式事务或加密算法作为通用业务代码。
### 第6章 代码/语法层
#### 6.1 定义、组成与划分标准

- **定义**：代码/语法层将逻辑映射为受语言类型系统、运行时和硬件约束的可执行语句，并保证资源与错误行为确定。
- **组成单位**：语句、表达式、类型、声明、指令、内存对象、线程/任务、异常、资源和构建配置。
- **划分标准**：以语言规范、运行时语义、目标平台和资源生命周期为依据；语法技巧不得改变上层契约或隐藏业务规则。
- **版本基线**：使用仍在支持期内的语言与运行时版本，固定工具链和依赖锁文件，升级通过兼容测试而非复制旧版本惯用法。
#### 6.2 设计规则（高效、简洁、安全、合理）

| 维度 | 强制规则 |
| --- | --- |
| 高效 | 依据剖析选择批处理、缓冲、零拷贝或对象复用；避免默认开启昂贵反射、序列化和无界并行。 |
| 简洁 | 使用当前语言的标准类型、集合、时间与并发抽象；遵循团队格式化结果，不写依赖隐式优先级的聪明表达式。 |
| 安全 | 开启严格类型、空值、边界、溢出和未初始化检查；不可信输入先限制长度和结构，再解析或反序列化。 |
| 合理 | 明确所有权、可变性、生命周期、错误类别和资源释放在每个执行路径上的语义。 |

- **类型安全**：公开边界避免裸映射和任意类型；金额禁止二进制浮点，时间使用瞬时类型并配套 IANA 时区，标识符不得参与浮点运算。
- **数值安全**：检查加减乘、类型收窄、位移、除零和最小负数取反；外部长度在分配内存前验证，整数转索引前检查上下界。
- **内存安全**：优先 RAII、作用域绑定、`defer`/`using` 或自动内存管理；手工内存语言必须定义唯一所有权与合法借用周期。
- **数据布局**：对象大小、虚调用、内联、逃逸和缓存行为只在性能模型需要时关注，不改变语义换取未经验证的布局优化。
- **可变状态**：默认不可变；共享可变状态必须由锁、消息传递或经过证明的同步原语保护，禁止靠“当前不会并发”的假设。
#### 6.3 并发、异常与资源规范

- **任务模型**：使用结构化并发或有界执行器；子任务有父级取消和截止期限，禁止请求结束后遗留无归属后台任务。
- **线程与连接**：不得为每个请求创建线程或无界任务；池大小依据资源容量和等待时间设定，队列必须有界并支持背压。
- **锁规则**：锁保护不变量而非整段业务；统一锁顺序、缩小临界区，锁内不得调用未知回调、网络或阻塞 I/O。
- **原子规则**：原子变量只保护其定义的同步关系；多变量不变量不能靠分别原子更新保证，复合检查再执行必须由同一同步域保护。
- **取消规则**：取消是协作式协议，I/O 和等待必须响应取消；清理代码不得因取消而跳过关键资源释放。
- **异常边界**：在模块边界转换为稳定错误类型，保留因果链和上下文；禁止捕获根异常后继续以未知状态运行。
- **资源释放**：文件、套接字、事务、锁、临时文件和响应体均在确定作用域释放；释放失败需记录且不能覆盖原始错误。
- **终止规则**：不使用线程强杀、进程内 finalizer 或析构猜测完成关键业务；关键清理必须显式、可测试且有超时。
#### 6.4 静态检查与验收标准

| 检查类别 | 最低要求 |
| --- | --- |
| 格式与编译 | 自动格式化无差异；编译器推荐警告开启，新增代码不得引入被压制的警告。 |
| 类型与语义 | 严格类型检查通过；禁止任意反序列化、危险动态执行、隐式全局和不安全强制转换。 |
| 静态安全 | SAST、密钥扫描、依赖漏洞与许可证检查无未接受的阻断项，例外必须有人、期限和补偿控制。 |
| 动态安全 | 手工内存或高性能关键路径按适用性运行 ASan/UBSan/TSan、模糊测试和竞争检测。 |
| 构建供应链 | 锁定依赖、生成 SBOM、校验制品来源和签名，构建可重复且版本信息可追踪。 |
| 性能回归 | 关键基准有资源预算；超过既定延迟、分配或内存回归阈值时不得静默合入。 |

- **验收证据**：静态检查报告、测试报告、依赖清单、构建环境、例外审批和性能基准与制品摘要关联。
- **日志要求**：错误日志包含操作、可关联 ID 和失败类别，不记录密钥、完整凭证、敏感负载或可直接利用的内部细节。
#### 6.5 反模式清单

- 依赖未定义行为、实现细节、默认编码、默认时区或字典偶然顺序。
- 以空指针、魔数或全局可变单例表达业务状态，以强制转换绕过类型系统。
- 无界创建线程、协程、定时器、缓冲区或重试任务，把背压留给运行时。
- 在析构/finalizer 中提交事务、发送网络请求或释放唯一业务凭证。
- 捕获异常后只打印继续执行，或在 `finally` 中覆盖原始返回值和异常。
- 为兼容旧习惯继续使用已淘汰 API，关闭编译警告、类型检查和安全检测。
### 第7章 基础设施层
#### 7.1 定义、组成与划分标准

- **定义**：基础设施层为应用提供计算、网络、存储、中间件、交付和运行保障能力，并量化其容量与故障边界。
- **组成单位**：主机、虚拟机、容器、Kubernetes、网络、负载均衡、数据库、缓存、消息系统、对象存储、DNS、可观测平台与云资源。
- **划分标准**：按平台责任、故障域、数据持久性、性能特征和运维边界划分；资源规格由工作负载和 SLO 推导，而非复制模板。
- **制品基线**：资源清单、拓扑与故障域图、容量模型、IaC、网络策略、资源配额、运行手册、备份与灾备方案。
#### 7.2 容量规划与选型规则

| 维度 | 强制规则 |
| --- | --- |
| 高效 | 用峰值到达率、服务时间、数据增长和批处理窗口推导容量；稳态保留不少于约 30% 的可验证余量，突发场景另行压测。 |
| 简洁 | 优先少量标准化计算、数据库和存储规格；每增加一种中间件都必须有现有组件无法满足的证据。 |
| 安全 | 默认私有网络、最小安全组、传输加密、资源配额和租户隔离；管理面与数据面分离，公开入口最小化。 |
| 合理 | 按延迟、吞吐、持久性、一致性、恢复目标和总拥有成本联合选型，不能只按产品流行度或峰值跑分。 |

- **容量公式**：依据 Little 定律 `并发量 L = 到达率 λ × 平均驻留时间 W`，再叠加尾延迟、峰值系数、故障转移和余量；不能只用平均 CPU 推算。
- **扩展判据**：无状态服务优先水平扩展；有状态组件先验证连接、I/O、存储和副本瓶颈，扩展测试必须覆盖单故障域退出后的容量。
- **网络选型**：记录跨区/跨地域 RTT、带宽、包速率、DNS、TLS 和出口成本；同步关键链避免不必要跨地域，东西向流量纳入容量模型。
- **存储选型**：事务与约束用关系库，海量简单键值用 KV，非结构化大对象用对象存储，时间序列与宽表仅在访问模式匹配时采用。
- **存储指标**：分别标注 IOPS、吞吐、P99 延迟、耐久性、可用性、一致性、单对象上限和 RPO/RTO；不得把“多副本”当作备份。
- **数据生命周期**：定义热温冷分层、保留、归档、删除、法定留存和销毁证明；索引、日志、快照与缓存同样纳入增长预测。
#### 7.3 容器与 Kubernetes 资源规范

- **镜像**：使用最小且受支持的基础镜像，固定不可变摘要，非 root 运行，只读根文件系统优先，删除 shell 和构建工具等非运行必需内容。
- **Requests**：CPU/内存请求基于压测和长期观测设置，调度必须能在单节点或单故障域退出时承载关键副本。
- **Limits**：内存上限需防泄漏失控并评估 OOM 风险；CPU 上限需评估节流和尾延迟，不得仅凭模板设置相同值。
- **探针**：readiness 判断是否接流量，liveness 只判断进程是否需要重启；liveness 不得依赖数据库等下游，否则易形成群体重启。
- **优雅终止**：配置 `preStop`、终止宽限期、连接排空和任务取消；终止流程必须先摘除流量，再停止接收并完成或放弃在途工作。
- **弹性**：HPA 优先使用能反映真实压力的 RPS、队列深度或并发指标；CPU 指标仅在相关时采用，并设置稳定窗口与扩容上限。
- ** disruptions**：关键服务配置多副本、反亲和、拓扑分布和 PDB；PDB 只约束自愿干扰，不能替代跨故障域容量。
- **配置与密钥**：配置与镜像分离，密钥进入专用密钥系统并限制挂载和读取；不得把密钥写入镜像、环境转储或日志。
- **资源治理**：命名空间配置 ResourceQuota 和 LimitRange，批任务与在线服务隔离；特权容器和宿主机挂载默认禁止并需例外审批。
#### 7.4 可观测性、度量与验收

| 维度 | 指标与规则 |
| --- | --- |
| RED | 每个请求驱动服务采集 Rate、Errors、Duration；按路由、状态和依赖分解，P99 不能只取各实例 P99 的平均。 |
| USE | 每类资源采集 Utilization、Saturation、Errors；CPU 同时观察节流，存储同时观察队列与尾延迟。 |
| 黄金信号 | 延迟、流量、错误、饱和度必须与服务 SLO 和追踪关联，告警针对症状与错误预算而非所有瞬时波动。 |
| 日志 | 结构化、分级、可关联，限制采样和保留期；脱敏且控制高基数字段，不以日志替代所有指标。 |
| 指标 | 统一名称、单位和标签；禁止 userId、orderId 等无界标签，记录采集缺口与基数成本。 |
| 追踪 | 入口、服务、消息和存储调用共享上下文；关键业务路径全量或尾部采样，普通路径受控采样。 |

- **容量验收**：在峰值、峰值叠加单副本故障、数据增长预测和依赖降级四种场景完成压测，SLO 与资源余量同时达标。
- **发布验收**：IaC 无未审查漂移，镜像和配置可回滚，探针/终止/PDB/配额通过故障注入验证。
- **告警验收**：每条 paging 告警有负责人、影响、阈值依据和运行手册；重复、无动作和长期静音告警必须清理。
- **成本验收**：按服务核算计算、存储、网络和可观测成本，闲置与超配资源有回收责任人和复核周期。
#### 7.5 反模式清单

- 按历史峰值永久堆机器，没有到达率、数据增长和故障转移模型。
- 所有容器共用同一 requests/limits，或将 HPA 最小副本设为 1。
- liveness 检查全部下游，数据库短暂故障引发全集群重启。
- 将多副本、快照、云盘耐久性或跨区复制等同于可恢复备份。
- 为每个团队引入不同数据库、消息系统和网关，却无独立值班能力。
- 采集无界高基数指标和完整敏感日志，监控成本与风险超过业务收益。
### 第8章 架构方案标准
#### 8.1 高性能设计规则

- **优化顺序**：先建立 SLO 与端到端剖析，再依次消除无谓工作、优化算法和访问路径、引入缓存/批处理/异步，最后扩容硬件。
- **预算分配**：将端到端 P99 预算拆到网关、应用、缓存、数据库和外部依赖；各段预算按串行关键路径求和，并保留队列与重试余量。
- **尾延迟**：同时观测排队、GC、连接获取、磁盘和锁等待；平均值或 CPU 利用率不能作为性能验收结论。

| 技术 | 设计规则 | 必测风险 |
| --- | --- | --- |
| CDN/客户端缓存 | 仅缓存可公开或按授权维度隔离的内容；使用 ETag/Cache-Control，个性化与私密响应明确禁止共享缓存。 | 缓存键越权、失效不及时、源站回源风暴 |
| 进程内缓存 | 适合小规模、可短暂过期数据；设置条目数/字节上限和 TTL，集群各实例允许有界不一致。 | 内存膨胀、实例间不一致、热点过期抖动 |
| 分布式缓存 | 缓存键包含租户、版本和必要授权维度；默认 TTL 加随机抖动，空值短缓存防穿透。 | 热 key、大 key、雪崩、缓存与源库不一致 |
| 缓存一致性 | Cache-Aside 由写库成功后失效缓存；强一致诉求不能靠双写无协调实现，必要时直读主库或采用版本协议。 | 并发回填旧值、删除失败、双写部分成功 |
| 请求合并 | 对同 key 回源采用 singleflight/租约，限制等待者数量和回源超时，防止一个慢请求无限堆积。 | 等待队列、锁持有者故障、错误结果被共享 |
| 异步化 | 仅将可延后且结果可追踪的工作移出请求；生产者使用事务性 outbox，消费者幂等并支持重放。 | 丢失、重复、乱序、积压、死信与结果查询 |
| 批处理 | 同时按记录数、字节数和等待时间设上界；超过任一阈值即提交，单批失败需可拆分定位。 | 大批超时、队头阻塞、内存峰值、部分失败 |
| 连接池 | 全实例连接总数小于下游安全容量；获取连接有超时，池等待队列有界并暴露饱和度。 | 连接泄漏、池耗尽、重试放大、跨池争抢 |
| 读写分离 | 只扩展可容忍副本延迟的读；写后读、支付和库存等按一致性要求走主库或带读位点。 | 副本延迟、读己之写失败、主库故障后语义变化 |
| 分库分表 | 在索引、查询、归档、垂直扩展和连接治理均不足，且持续容量或 SLO 证据明确时实施。 | 跨片查询、热点分片、分布式事务、扩容迁移 |

- **分片判据**：至少明确数据规模/增长、访问键、热点、事务范围、路由、全局 ID、迁移、再均衡、跨片查询和运维方案；单表行数不是唯一阈值。
- **背压规则**：所有队列、线程池、批窗口和缓冲区必须有上界；过载时按业务等级拒绝、降级或延后，不允许内存无限吸收流量。
- **降级数据**：缓存、搜索索引、物化视图必须标明权威源、最大陈旧时间和重建方式；非权威数据不可成为不可恢复的唯一副本。
#### 8.2 高可用设计规则

| 控制 | 强制规则 |
| --- | --- |
| 冗余 | 无状态服务跨至少两个独立故障域，关键服务优先三个；共享电源、网络、控制面或单集群不得伪装独立冗余。 |
| 故障转移 | 明确探测、判定、切换、回切和脑列防护；副本未达恢复点要求时不得自动提升为主。 |
| 健康检查 | 区分进程存活、可接流量和依赖健康；摘除需有防抖，恢复需渐进接流，避免 flap。 |
| 超时 | 每跳超时小于调用方剩余预算，包含连接、写入、响应头和响应体；禁止无限等待。 |
| 重试 | 只对幂等或可去重操作重试，采用指数退避＋随机抖动；默认最多 1～2 次，且受总截止时间与重试预算约束。 |
| 熔断 | 依据滑动窗口错误率、慢调用和最小样本量触发；半开状态用小流量验证，恢复后逐步放量。 |
| 降级 | 预先定义只读、默认值、简化功能或人工路径；安全、支付和权限决策不得使用可能越权的默认成功。 |
| 限流与卸载 | 按租户、接口、成本和系统容量多维限流；先保核心路径，低优先级任务可暂停，拒绝响应须轻量。 |
| 隔离 | 按租户、依赖和关键性使用舱壁式线程池、连接池、队列或集群；限制单个租户消耗。 |
| 混沌工程 | 在稳态假设、爆炸半径、停止条件和回滚明确后，注入实例、可用区、延迟、丢包、DNS、磁盘和时钟故障。 |

- **重试预算**：初始可将重试流量限制在原请求的 10% 以内并按实测调整；多层调用只允许一层主导重试，避免指数放大。
- **对冲请求**：仅用于可幂等且极重尾延迟的读，必须延迟小段时间后发送、取消慢分支并计入额外负载预算。
- **故障转移验收**：不能只验证“切换成功”，还须验证 DNS/连接缓存刷新、在途请求、数据损失、脑列和回切后的容量。
- **变更可用性**：滚动、蓝绿或金丝雀发布必须支持向后兼容、自动停止和快速回滚；数据库变更采用扩展—迁移—收缩顺序。
#### 8.3 高可靠与一致性设计规则

| 需求 | 选择规则 |
| --- | --- |
| 线性一致 | 用于必须看到最新单一事实且可接受协调成本的关键状态，由支持相应语义的事务或共识存储实现。 |
| 读己之写 | 会话内读取使用主库、复制位点或版本令牌；不得依赖固定等待若干毫秒。 |
| 因果一致 | 有因果关系的操作保持顺序，无关操作可并行；消息分区和向量/版本信息必须与业务语义一致。 |
| 最终一致 | 仅用于可容忍陈旧且有收敛规则的数据，公布最大预期收敛时间和对账机制。 |
| 本地事务 | 单库内用原子提交和约束保护不变量，事务内不得包含远程调用、消息发送或长耗时计算。 |
| Saga | 跨服务业务拆成可补偿本地事务，每步有幂等、超时和补偿；补偿是反向业务动作，不是数据库时间倒流。 |
| Outbox/Inbox | 业务写与 outbox 同事务，投递至少一次；消费者以 inbox/唯一键去重，处理与去重记录保持原子性。 |
| 对账 | 定期比较权威账、派生账和外部账单，差异分级、自动修复可证明项，其余进入人工闭环。 |

- **幂等层次**：协议幂等键防止请求重复，业务唯一约束防止实体重复，状态机防止非法重复迁移，三者不能相互替代。
- **顺序规则**：需要顺序的实体使用分区键和单调版本；消费者拒绝旧版本，对暂不可处理的乱序事件采用重试或暂存，不直接覆盖新状态。
- **资金与库存**：采用不可变流水、条件扣减、余额/库存守恒校验和独立对账；缓存、消息或搜索副本不是最终账本。
- **备份基线**：执行 3-2-1-1-0 思路，至少三份副本、两种介质、一份异地、一份离线或不可变、恢复验证零错误；具体保留按风险与法规确定。
- **恢复能力**：同时定义 RPO、RTO、点恢复、区域灾难和误删恢复；备份成功日志不计为恢复成功，必须定期做隔离环境恢复演练。
- **数据修复**：修复脚本需有备份、影响行数预估、幂等、审批、审计和回滚/补偿方案；禁止直接无约束修改权威账。
#### 8.4 量化指标与 SLO 预算

| 可用性目标 | 365 天最大不可用 | 30 天最大不可用 | 7 天最大不可用 |
| --- | ---: | ---: | ---: |
| 99.9% | 8.76 小时 | 43.2 分钟 | 10.08 分钟 |
| 99.95% | 4.38 小时（262.8 分钟） | 21.6 分钟 | 5.04 分钟 |
| 99.99% | 52.56 分钟 | 4.32 分钟 | 1.008 分钟 |
| 99.999% | 5.256 分钟 | 25.92 秒 | 6.048 秒 |

- **SLI 示例**：`可用性 = 有效且成功的请求数 / 有效请求总数`；必须定义有效请求、成功状态、延迟阈值、测量点和排除窗口，不得先剔除不利故障。
- **错误预算**：`错误预算 = 有效请求数 × (1 - SLO)`；预算快速消耗时冻结高风险变更，恢复后仍需完成根因与复发预防。
- **延迟预算**：P99 以端到端用户操作为准；示例 300ms 串行关键路径可分配为网关 20ms、应用编排 70ms、领域计算 40ms、缓存/数据库 100ms、序列化与网络 40ms、余量 30ms。
- **依赖预算**：并行依赖取关键路径最大值而非简单相加；任何重试、排队和连接获取都必须包含在其所属阶段预算中。
- **可靠指标**：数据错误率、重复处理率、对账差异率、乱序拒绝率、恢复成功率、RPO/RTO 达标率均设独立阈值，不能由可用性替代。
- **演练频率**：核心恢复与故障转移至少按季度演练，重大架构或数据变更后追加；以实测恢复时间和数据点更新预案。
#### 8.5 架构方案验收清单

- [ ] 是否有业务驱动、约束、备选方案、权衡和退出条件的 ADR，而非只有产品拓扑图？
- [ ] 是否完成峰值、尾延迟、单故障域退出、依赖降级和数据增长场景压测？
- [ ] 所有外部调用是否有超时、取消、幂等、重试边界和可观测上下文？
- [ ] 所有队列、连接池、缓存、批任务和分页是否有资源上界与背压？
- [ ] 权威数据、一致性、去重、乱序、补偿、对账和修复责任是否明确？
- [ ] 是否验证故障转移、脑列、回切、备份恢复和区域灾难，而非只检查配置？
- [ ] SLO、错误预算、告警、值班、运行手册和演练证据是否关联到同一服务？
- [ ] 新增组件和复杂度是否有可量化收益、负责人和退役方案？
### 第9章 端到端示范：通用电商下单与商品读取
#### 9.1 战略与业务层结构

- **目标**：提升有效下单转化率，同时以支付成功率、取消率、超卖率、退款率和单笔履约成本作为护栏。
- **能力地图**：商品目录、价格、库存、订单、支付、履约、售后；营销推荐作为独立支撑能力，不进入库存权威边界。
- **价值流**：商品可售确认 → 订单创建 → 库存预占 → 支付确认 → 履约指令 → 订单完成；取消/超时进入释放或补偿流。
- **优先级**：正确性红线为不超卖、不重复扣款、不重复建单；性能优化不得绕过唯一约束、状态机或对账。
- **关键结果**：下单接口可用性 99.95%，创建订单 P99 不高于 500ms，支付与订单差异在规定对账窗口内闭环，具体业务目标以基线设定。
#### 9.2 应用/解决方案层结构

| 服务 | 唯一职责与数据 | 主要契约 |
| --- | --- | --- |
| 商品目录 | 商品展示、上下架与读取模型，不拥有可售库存 | `GET /v1/products/{id}`，游标列表，商品变更事件 |
| 订单 | 订单聚合、价格快照、订单状态机、Saga 编排 | `POST /v1/orders` 强制幂等键，`GET /v1/orders/{id}` |
| 库存 | 库存账本、条件预占、释放与确认 | 预占/释放命令，库存结果事件，业务单号唯一约束 |
| 支付 | 支付单、支付适配与状态查询，不保存网关多余敏感信息 | 支付请求、回调验签、支付事件、主动对账 |
| 履约 | 支付后履约指令和履约状态 | 履约命令与状态事件，支持重复命令去重 |

- **集成规则**：订单服务通过应用层编排库存与支付；支付网关经防腐层适配，第三方错误码和字段不得进入订单领域。
- **事务规则**：订单写库与 `OrderCreated` outbox 同事务；事件至少一次投递，库存、支付和履约均以业务单号去重。
- **API 规则**：创建订单同幂等键同请求重放原订单，同键不同请求体返回 409；商品列表采用稳定游标，错误响应携带 `requestId`。
- **一致性规则**：订单与库存/支付采用最终一致和 Saga；订单本地聚合内部强一致，商品展示可接受有界陈旧。
#### 9.3 程序/模块层结构

```text
order-service
├─ interfaces       HTTP/消息适配、认证上下文、请求响应转换
├─ application      CreateOrderHandler、事务边界、Saga 编排、端口
├─ domain           Order、OrderLine、Money、OrderStatus、领域规则
└─ infrastructure   数据库、Outbox、库存/支付客户端、时钟与配置实现
```

- **依赖规则**：`interfaces → application → domain`，`infrastructure → application/domain 端口`；domain 不导入 HTTP、ORM 或消息 SDK。
- **组合根**：在启动入口装配数据库、时钟、ID、客户端和消息适配器；领域代码不自行创建网络客户端。
- **公共契约**：Order 只能通过应用服务或领域方法修改，外部模块不能直接写订单表或调用私有 repository 实现。
- **架构测试**：禁止循环依赖、跨模块表访问和领域层框架导入；公共端口变化触发契约与兼容测试。
#### 9.4 单元/函数层结构

| 单元 | 契约与测试重点 |
| --- | --- |
| `CreateOrderHandler` | 编排一次用例；校验幂等、开启本地事务、保存订单和 outbox，不包含价格计算细节。 |
| `Order.place` | 验证至少一行、数量正整数、币种一致并生成价格快照；拒绝非法初始状态。 |
| `Money` | 不可变值对象，使用最小货币单位或十进制；验证币种、精度、舍入、溢出和异币种相加。 |
| `PriceCalculator` | 纯函数计算行小计与总额；优惠规则以显式策略输入，不读取数据库或当前时间。 |
| `OrderStatus` | 状态迁移集中于领域方法；非法迁移返回明确领域错误并保留当前状态。 |

- **测试边界**：空订单、零/负数量、超大金额、跨币种、重复商品行、舍入边界、重复请求、乱序回调和非法状态迁移必须覆盖。
- **副作用隔离**：应用服务注入时钟与 ID 生成器；纯领域测试不依赖真实网络、数据库、系统时间或随机源。
#### 9.5 算法/逻辑层结构

- **定价逻辑**：逐行按声明精度计算小计，再按统一顺序汇总与舍入；使用参考实现验证守恒，禁止二进制浮点金额。
- **库存逻辑**：以 `可用量 >= 请求量` 的条件原子更新完成预占，业务单号唯一；重复预占返回首次结果，释放仅对有效预占执行一次。
- **状态机**：`PENDING → INVENTORY_RESERVED → PAID → FULFILLING → COMPLETED`；`PENDING/INVENTORY_RESERVED` 可按规则进入取消/过期，终态拒绝普通迁移。
- **补偿规则**：支付失败后释放库存；释放失败进入有界重试与人工/自动对账，不直接删除订单或库存流水。
- **读取算法**：商品热点使用 CDN＋进程内短缓存＋分布式缓存；同 key singleflight 回源，TTL 加抖动，空结果短缓存。
- **保护算法**：创建订单按租户和账户使用令牌桶；库存热点路由以商品键保持顺序，缓存路由使用一致性哈希，布隆过滤器只作不存在预筛。
#### 9.6 代码/语法层结构

- **类型**：`OrderId/ProductId/Money/Instant` 使用明确类型；金额不以 `double/float` 表示，时间存储 UTC 瞬时并在展示层转换时区。
- **资源**：数据库事务、连接、HTTP 响应体和消息句柄使用作用域释放；事务内不调用库存或支付远程接口。
- **并发**：库存预占由存储条件更新保护；订单聚合使用版本字段做乐观并发控制，版本冲突返回可识别错误。
- **异常**：库存不足、状态冲突和上游超时分别映射稳定错误；保留因果链，不向客户端泄露 SQL、堆栈或支付敏感数据。
- **取消**：HTTP 取消和截止时间传入存储与客户端；Saga 异步步骤使用独立可追踪生命周期，不依附已结束请求的临时线程。
- **检查**：严格类型、格式化、静态安全、依赖扫描、竞态/资源检测和关键定价基准全部纳入合并门禁。
#### 9.7 基础设施层结构

- **计算**：无状态服务跨故障域多副本，按 RPS 和并发扩缩容；单故障域退出后的剩余容量仍满足核心下单与商品读取 SLO。
- **数据**：订单、库存、支付账本使用高可用事务库和 PITR；缓存不作为权威源，消息采用持久副本并监控积压和死信。
- **网络**：入口经负载均衡与 API 网关，数据库仅私有子网可访问；支付出站走受控出口，跨地域同步调用不进入核心下单链。
- **Kubernetes**：按压测设置 requests/limits、反亲和、PDB、readiness 和优雅终止；liveness 不检查数据库或支付网关。
- **可观测**：以 `traceId/orderId` 关联入口、outbox、消息、库存、支付和对账；orderId 只进入日志或追踪属性，不作为无界指标标签。
- **恢复**：订单与支付定期恢复演练，库存执行守恒对账，缓存可清空重建，消息重放有幂等和速率上限。
#### 9.8 端到端验收矩阵

| 场景 | 必须通过的验收 |
| --- | --- |
| 正常下单 | 仅生成一个订单和一条业务流水，状态迁移可追踪，P99 与可用性达到既定 SLO。 |
| 重复提交 | 同幂等键同请求返回原结果；同键不同负载冲突；无重复库存预占或支付。 |
| 库存不足/竞争 | 条件更新保证不出现负库存，失败订单不进入支付，热点竞争下数据库与对账一致。 |
| 支付超时/重复回调 | 不明确状态进入查询或对账，不默认成功；重复和乱序回调按版本与状态机处理。 |
| 消息重复/积压 | 消费者去重，积压触发背压和告警，重放不产生二次业务副作用。 |
| 缓存失效/雪崩 | 回源合并和限流保护数据库，缓存全失效仍可降级直读，恢复过程无请求风暴。 |
| 单实例/单可用区故障 | 核心请求在错误预算内恢复，剩余容量达标，无脑列和未授权默认成功。 |
| 误删与灾难恢复 | 在批准 RPO/RTO 内恢复权威数据，恢复后订单—库存—支付对账闭环。 |
### 第10章 反模式与过时做法剔除
#### 10.1 架构与组织误判

- **微服务误判**：把团队沟通差、代码混乱或发布缓慢直接归因于单体；未先明确模块边界、自动测试和持续交付，拆分只会放大问题。
- **分布式单体**：服务必须成群发布、共享数据库、同步调用成链，既承担网络与运维成本，又失去独立部署收益。
- **过度设计**：无规模证据即引入多地域多活、多分片、服务网格、自研中间件、事件溯源或多层通用平台。
- **银弹误判**：把 DDD、六边形、K8s、Service Mesh、消息队列或 AI 生成代码当作质量保证，而不建立契约、测试和运行责任。
- **反向纠偏**：边界尚不稳定时退回模块化单体不是失败；以实际变化、SLO 和团队认知证据重新划界优于维持错误拆分。
#### 10.2 性能、可用性与可靠性误区

- 先加缓存再排查算法，导致陈旧、穿透和一致性问题超过原性能收益。
- 把所有操作异步化，却无结果查询、幂等、死信、重放和积压治理。
- 每层都超时重试，形成重试风暴；或无超时、无界队列等待下游恢复。
- 用平均延迟、平均 CPU、单实例跑分或一次压测证明容量充足。
- 把限流、熔断、降级配置成全局同一阈值，不区分核心与非核心业务。
- 宣称消息“恰好一次”、分布式锁“绝对安全”或多副本“永不丢数据”。
- 将备份任务成功等同于可恢复，从未验证恢复时间、数据点和业务一致性。
#### 10.3 代码与语言旧习惯

- **Java 终结机制**：不再以 `finalize()` 释放关键资源，改用显式关闭、try-with-resources 或 Cleaner 只做受控兜底。
- **Java 线程控制**：不使用 `Thread.stop/suspend/resume`，改用协作取消、中断、结构化任务和超时。
- **Java 日期时间**：新代码不使用 `Date/Calendar/SimpleDateFormat` 建模现代时间逻辑，采用 `java.time` 的 `Instant`、带时区类型与明确格式。
- **Java 类型与并发**：不使用原始类型容器、无界线程池或非 volatile 的双重检查锁定；优先安全发布、不可变对象和成熟并发原语。
- **通用资源习惯**：不依赖析构顺序、finalizer、进程退出钩子完成关键业务提交，不忽略异常或依赖默认编码/时区。
- **通用语法习惯**：不保留已停止支持运行时的补丁和 workaround 作为新代码模板；升级后删除无用兼容层并运行完整验证。
#### 10.4 最终剔除准则

- 任何无法关联业务结果、正确性、SLO、成本或风险收益的结构与组件，均不得仅因“先进”而保留。
- 任何无法说明权威数据、失败语义、恢复方式和责任人的方案，均不得进入生产。
- 任何只靠口头约定、人工记忆或单次演示维持的规范，均须转化为自动检查、契约测试、运行手册或可审计演练。
- 任何优化若未提供等价性证据、基准结果和回退路径，均不得以性能名义合入。
- 任何阈值都应按业务风险和实测基线校准；保留决策记录，禁止把示例数值包装成跨行业绝对定律。

## 第二篇 服务器操作系统底层逻辑与服务部署规范

### 1. 操作系统底层运行逻辑

#### 1.1 进程、线程与程序装载

- Linux 以 `task_struct` 描述可调度任务；进程提供地址空间、凭据、文件描述符表和信号处置等资源边界，线程共享这些资源但拥有独立寄存器、栈、调度状态和线程本地存储。
- `fork/clone` 创建任务时采用写时复制，`execve` 重新装载程序；PID 标识线程，TGID 标识用户视角的进程，父子关系决定退出状态回收与僵尸进程处理。
- ELF 装载器建立代码段、数据段、堆、栈、`mmap` 区和 vDSO 映射；动态链接器解析共享库、重定位和符号，ABI 决定调用约定、对象布局、对齐和系统调用接口。
- 编译、汇编、链接、装载是不同边界；运行库的初始化、堆分配器、垃圾回收、虚函数分派和对象复制均可能产生隐含指令与内存开销，不能仅以源码行数推断成本。
- 线程是调度单位，进程不是天然并发上限；CPU 密集任务的有效并行度受可用核数约束，I/O 密集任务还需受连接、内存和下游容量约束。
- **对应用的工程含义：**线程池、进程数和连接池必须容量化；多线程进程调用 `fork` 后、执行 `exec` 前只使用异步信号安全函数；动态库版本、CPU 指令集和 libc 兼容性须纳入发布校验。
- **对应用的工程含义：**父进程必须回收子进程，服务管理器应收割孤儿进程；崩溃转储、ASLR、调试符号和依赖库路径按安全策略配置，不在不可信程序上直接运行 `ldd`。

#### 1.2 调度、优先级与 CPU 亲和性

- Linux 普通任务由公平调度类管理，通常统称 CFS；较新内核采用 EEVDF 实现公平选择，核心目标是按权重分配 CPU 并控制调度延迟，而非固定时间片轮转。
- `SCHED_OTHER` 承载常规业务，`SCHED_BATCH/SCHED_IDLE` 用于后台任务；`SCHED_FIFO/SCHED_RR` 是实时策略，可能长期抢占普通任务和关键内核线程，未经实时性验证不得启用。
- `nice` 范围通常为 -20～19，数值越大 CPU 权重越低；容器和多租户主机优先使用 cgroup v2 `cpu.weight`、`cpu.max` 控制相对权重和带宽上限。
- 运行队列过长表示可运行任务等待 CPU；自愿切换通常源于锁或 I/O 等待，非自愿切换通常源于抢占，二者必须与吞吐量、尾延迟共同判断。
- 亲和性通过 `taskset`、cpuset 或运行时 API 限制 CPU 集合；NUMA 内存遵循首次触碰等策略，跨节点访问和线程迁移会破坏缓存局部性。
- IRQ、`ksoftirqd`、工作线程和业务线程争用同一核心会形成抖动；网卡多队列、RPS/RSS、IRQ 绑定与应用绑核必须整体设计，禁止零散手工绑定后无记录运行。
- **对应用的工程含义：**先减少无效计算、锁竞争和线程数，再考虑绑核；为中断和系统任务预留核心，使用 `numactl` 同时约束 CPU 与内存节点，并以 p99 延迟而非平均利用率验收。
- **对应用的工程含义：**容器 CPU limit 可能引发周期末限流，延迟敏感服务应检查 throttling 后决定调大 limit、减少并行度或仅设置 requests，不得盲目复制“禁用 CPU limit”做法。

#### 1.3 虚拟内存、分页、缺页与大页

- 虚拟地址经多级页表转换为物理地址，TLB 缓存转换结果；常见基础页为 4 KiB，具体页大小和页表层级依架构与内核配置而定。
- `mmap` 或堆扩展先建立虚拟映射，首次访问触发缺页； minor fault 无需磁盘 I/O，major fault 需从后备存储读页，匿名页、文件页和写时复制页的故障成本不同。
- RSS 包含共享页且各进程重复计数，PSS 按比例分摊共享页，USS 更接近进程独占回收量；容量规划不得直接累加 RSS，也不得把 `MemFree` 当作全部可用内存。
- 内存回收包括页缓存回收、匿名页换出和直接回收；kswapd 后台回收不足时，申请线程同步等待，表现为突发延迟，严重内存不足最终触发全局或 cgroup OOM。
- swap 提供内存压力和 OOM 之间的缓冲，但换入换出会引入磁盘延迟；已占用 swap 不等于当前故障，持续 `si/so`、PSI memory stall 和 major fault 才是重点。
- 透明大页 THP 通常减少 TLB 未命中和页表遍历，也可能造成内存碎片、压缩延迟和额外驻留；静态 HugeTLB 页需预留并挂载，适合明确支持的大内存应用。
- **对应用的工程含义：**JVM、数据库等固定堆必须计入元空间、线程栈、直接内存和页缓存，并置于容器 limit 之下；禁止通过关闭 OOM、无限 overcommit 或扩大 swap 掩盖容量缺口。
- **对应用的工程含义：**数据库、JVM 等按官方支持矩阵选择 `madvise`、禁用 THP 或静态大页；调整前后同时比较 TLB miss、内存驻留、压缩耗时和 p99，而非只看吞吐。
- **对应用的工程含义：**热数据按工作集估算，使用对象池仅限已证实的热点；读取 `/proc/<pid>/smaps_rollup`、`/proc/meminfo` 和 cgroup `memory.stat` 定位构成，不凭任务管理器单值调参。

#### 1.4 文件系统、VFS、PageCache 与写回

- VFS 以 superblock、inode、dentry 和 file 抽象不同文件系统；文件描述符指向打开文件描述，偏移量是否共享取决于描述符复制方式，路径解析、权限检查和实际磁盘访问是不同成本。
- 普通读写默认经过 PageCache，预读提升顺序访问吞吐；缓存页可被回收，`free` 中 `buff/cache` 通常可在压力下复用，不应定时执行 `drop_caches`。
- `write` 成功通常只表示数据进入页缓存；后台写回将脏页落盘，`fsync/fdatasync` 提供文件数据及必要元数据的同步点，替换文件时还需关注目录项持久化。
- 日志文件系统主要保障元数据一致性，不自动保证应用数据完整；磁盘、RAID、云盘和数据库的缓存策略必须支持屏障/FUA，禁止以不安全写缓存换取基准成绩。
- `O_DIRECT` 绕过页缓存并常有地址、长度和偏移对齐要求，不天然更快；数据库自行缓存时可评估使用，普通服务优先使用缓冲 I/O 和合适预读。
- **对应用的工程含义：**关键配置采用“临时文件写入—检查—`fsync`—原子 `rename`—必要时同步目录”流程；上传和下载设置大小、超时、磁盘配额及 inode 上限。
- **对应用的工程含义：**日志高吞吐时优先批量写、异步刷盘与独立磁盘，但必须声明可丢失窗口；小文件过多应合并或分目录，监控 inode、目录项缓存和打开文件数。
- **对应用的工程含义：**数据盘采用 `noatime` 或 `relatime` 前确认依赖，容器挂载显式区分只读配置与可写数据；禁止把 NFS 作为数据库数据目录，除非产品和存储组合明确认证。

#### 1.5 I/O 模型与事件通知

- 阻塞 I/O 在数据未就绪时睡眠，编程简单但每个并发流独占执行资源；非阻塞 I/O 返回 `EAGAIN/EWOULDBLOCK`，须由事件循环驱动并处理短读、短写和背压。
- `select/poll` 是就绪通知，通常每次扫描大量描述符；`epoll` 在内核维护兴趣集合并按就绪事件返回，适合 Linux 高并发，但不等于所有操作都异步完成。
- `epoll` 水平触发可持续报告未处理就绪状态，边沿触发仅在状态变化时通知；边沿触发必须使用非阻塞描述符并循环读写至 `EAGAIN`，否则可能永久漏处理。
- 普通磁盘文件的 `epoll` 就绪语义不解决磁盘阻塞；Linux 文件异步 I/O 可评估原生 AIO 或 `io_uring`，须核对内核、运行时支持和故障恢复能力。
- Windows IOCP 是完成通知模型，先提交操作再接收完成结果；Linux `epoll` 与 FreeBSD `kqueue` 主要是就绪通知，不能按同一伪代码机械移植。
- `kqueue/kevent` 可统一监听描述符、信号、定时器等事件；跨平台服务应由成熟网络库封装事件后端，业务层只处理连接状态机和超时。
- **对应用的工程含义：**每个连接必须有读、写、空闲和总生命周期超时；发送缓冲区满时暂停读取上游或限流，禁止无限排队导致内存放大。
- **对应用的工程含义：**事件循环内不得执行阻塞 DNS、慢日志同步或重计算；线程池与事件循环交接必须有队列上限，描述符关闭后清除相关事件和定时器。

#### 1.6 网络协议栈与 Socket 生命周期

- TCP 服务端依次经历 `socket—bind—listen—accept`，主动连接经过三次握手进入 ESTABLISHED；SYN 队列与 accept 队列不同，应用 `backlog` 还受 `somaxconn` 上限约束。
- 数据发送经历 socket 缓冲、TCP/UDP、IP、qdisc 和网卡队列，接收方向经驱动、软中断、协议栈到 socket 缓冲；丢包可能发生在任一层，重传并不等同于物理网卡故障。
- 主动关闭方通常进入 TIME_WAIT，用于可靠终止和处理迟报文；CLOSE_WAIT 长期堆积通常表示被动关闭方未调用 `close`，不能仅靠内核参数消除。
- `SO_REUSEADDR` 用于既定绑定语义，不等于任意端口劫持；`SO_REUSEPORT` 允许多个监听 socket 分担连接，须验证四层哈希、热进程排空和升级兼容性。
- 每个 socket 占用描述符、缓冲和协议栈状态；出向连接受五元组、临时端口和 conntrack 容量约束，长连接复用通常比扩大端口范围更有效。
- **对应用的工程含义：**所有 `read/write/send/recv` 处理短操作和错误，连接池设置获取、空闲、建立和总超时；重试仅限幂等操作并采用指数退避、抖动和重试预算。
- **对应用的工程含义：**优雅停止先停止接收新连接，再完成在途请求，最后关闭空闲连接；`TCP_NODELAY` 仅用于已确认的小包延迟问题，优先通过应用批量写减少小包。
- **对应用的工程含义：**使用 `ss -ti`、`nstat`、`netstat -s`、网卡和 conntrack 指标区分握手、重传、丢包和应用堆积；TIME_WAIT 数量本身不是故障判据。

#### 1.7 系统调用与上下文切换开销

- 系统调用完成用户态到内核态切换、参数校验、用户内存复制和服务例程执行；返回时还可能处理信号与重新调度，开销不仅是模式切换指令。
- 上下文切换保存和恢复寄存器、栈及调度状态，跨进程还可能切换地址空间并扰动 TLB、缓存和分支预测；真实成本受工作集和 NUMA 影响，不能只用单次微基准外推。
- 时钟、缺页和设备中断是异步或同步进入内核的其他路径；硬中断应尽快完成，耗时工作由软中断、工作队列或线程承接。
- vDSO 可避免部分只读调用的完整进入内核；`readv/writev`、批量接口和 `sendfile` 可减少调用或复制，但须以剖析结果证明收益。
- **对应用的工程含义：**减少高频小读写、无意义状态查询和忙轮询；锁在无竞争时保留用户态 fast path，高竞争时应缩短临界区而不是依赖自旋。
- **对应用的工程含义：**高 `sys`、高非自愿切换或大量 futex 等待分别指向内核工作、CPU 过载和锁竞争；`strace` 会显著放大被跟踪进程开销，生产使用须限时、限 syscall 并审批。

#### 1.8 容器隔离与资源控制

- mount、PID、network、IPC、UTS、user、time 和 cgroup namespace 提供不同视图隔离；`chroot` 只改变路径视图，不构成完整安全边界。
- cgroup v2 统一控制 CPU、内存、I/O、PID 等资源；CPU quota 产生限流，memory limit 触发回收或 OOM，容器内读取宿主机总内存的旧运行时会错误扩容。
- capability 将 root 权限拆分，seccomp 过滤系统调用，`no_new_privs` 阻止提权，SELinux/AppArmor 施加强制访问控制；各层互补而非互相替代。
- 容器共享宿主机内核，内核漏洞、危险 capability、敏感宿主机挂载和过宽系统调用会突破最小权限边界；高隔离需求使用虚机或经评估的强隔离运行时。
- **对应用的工程含义：**默认非 root、只读根文件系统、删除全部 capability 后按需添加、`seccomp=RuntimeDefault`、禁用特权容器和宿主机 PID/网络命名空间。
- **对应用的工程含义：**Java、Go、.NET 等运行时须确认识别 cgroup 限制；监控容器 OOM、CPU throttling、PIDs 和 I/O 压力，不能只观察节点指标。
- **对应用的工程含义：**镜像内不包含编译工具、调试凭据和秘密；临时目录使用受控 `tmpfs`/emptyDir 并设大小，升级内核与运行时前验证 seccomp、网络和存储兼容性。

#### 1.9 FreeBSD 与 Linux 的关键差异

- FreeBSD 默认使用 ULE 调度器而非 Linux CFS/EEVDF；同样关注交互性、SMP、SMT 和亲和性，但优先级、实时任务及调优 sysctl 不可照搬 Linux。
- FreeBSD 提供 `kqueue/kevent`，Linux 提供 `epoll/io_uring`；两者事件语义和后端成本不同，跨平台网络库需分别压测。
- FreeBSD UFS 的 soft updates、快照与日志机制、ZFS 的 ARC 和写路径均有自身特征；ZFS ARC 不应按 Linux PageCache 的规则直接清理或计算。
- FreeBSD 以 jail 隔离文件系统、进程、网络和权限，以 `rctl` 控制资源；它不是 Linux namespace/cgroup 的同名替换，也不原生提供 Docker/OCI 运行体验。
- Linux capability/seccomp 对应思路在 FreeBSD 可结合 jail 和 Capsicum 能力模式实现；Capsicum 要求应用主动进入能力沙箱，不能把 seccomp 配置直接复用。
- FreeBSD 基础系统使用 `rc.conf` 与 rc.d，不使用 systemd；包管理使用 `pkg`/Ports，服务启动、依赖和日志配置须分别维护。
- 观测工具采用 `top`、`vmstat`、`iostat`、`systat`、`netstat`、`sockstat`、`truss`、`dtrace`、`pmcstat`；Linux 的 `ss`、`strace`、perf 与 BCC 命令不可直接套用。
- 防火墙常用 pf 或 ipfw，网络调优使用 FreeBSD 对应 sysctl；上线前按具体 FreeBSD 版本手册验证名称、默认值及支持周期。
- **对应用的工程含义：**保持业务层可移植，但安装脚本、服务单元、监控采集器、调优模板和故障手册必须按操作系统分别版本化与验收。

### 2. 性能分析与调优规范

#### 2.1 测量与变更顺序

- 先定义吞吐、延迟、错误率和资源成本基线，再按 USE（利用率、饱和度、错误）检查资源，按 RED（速率、错误、耗时）检查服务。
- 区分均值、峰值和分位数，统一采样窗口、实例范围及时钟；生产告警与压测结果使用同一指标定义，避免把节点均值掩盖的单实例热点遗漏。
- 调优顺序固定为：确认业务影响和可复现性→确认瓶颈层次→保留原始证据→优先修复应用与架构→一次只改一个变量→同负载对比→记录并准备回滚。
- 禁止凭单篇参数清单、单机瞬时 `top` 或“内存越少越好”调参；禁止同时修改内核、应用、实例数和流量后再宣称某项参数有效。
- 性能实验先在同构预发环境进行，生产灰度覆盖业务高峰；采集工具本身有开销，perf、eBPF、抓包和 strace 必须限定范围与时长。

#### 2.2 核心观察指标与初始阈值

- 下表是通用服务器告警起点，不是调参触发器；最终阈值须服从 SLO、硬件基线和工作负载，连续 5～15 分钟或采用多窗口燃尽告警，瞬时峰值单独记录。

| 维度 | 必看指标 | 初始预警 | 初始严重 | 判读约束 |
| --- | --- | --- | --- | --- |
| 负载 | load1/5/15 除以可用 vCPU、PSI cpu | 15 分钟比值 >1 或 PSI some >10% | 比值 >2 或 PSI some >50%，且伴随 SLO 退化 | Linux load 含不可中断睡眠，须拆分 CPU 与 I/O；CPU full 主要用于 cgroup |
| CPU | user/system/iowait/steal、运行队列 | 总利用率 >80% 持续 15 分钟 | >90% 且 SLO 退化 | system >30%、steal >10% 单独调查 |
| 调度 | ctx switch、非自愿切换、容器 throttled | 切换率显著偏离基线 | 限流持续且 p99 超标 | 无统一每秒切换次数上限 |
| 内存 | MemAvailable、cgroup usage、PSI、major fault | 可用内存 <10% | <5% 或 PSI full 持续 | 禁止仅按 MemFree 或 swap 占用告警 |
| 换页/OOM | `si/so`、pgfault/pgmajfault、OOM kill | 持续换页且延迟上升 | 任一关键服务 OOM | 数据库与缓存分别设置更严格阈值 |
| 文件系统 | 空间、inode、只读、挂载错误 | 空间或 inode >80% | >90% 或出现只读/错误 | 日志与数据分区可提前告警 |
| 块设备 | `await`、`aqu-sz`、util、读写错误 | SSD/NVMe await >10 ms | >20 ms 或介质错误 | HDD 可从 50/100 ms 起步，以应用 p95 为准 |
| 网络接口 | 带宽、drop、error、overrun、队列 | 利用率 >70% 或持续丢包 | >90% 或错误持续增长 | 丢包须定位 qdisc、驱动、协议栈或对端 |
| TCP | 重传率、重传耗时、连接状态、监听溢出 | 重传段占比 >2% | >5% 且伴随超时 | 长肥网络与无线链路需独立基线 |
| 端口/连接跟踪 | 临时端口、conntrack、FD 使用率 | 任一达到上限 80% | 达到 90% 或分配失败 | 优先连接复用，TIME_WAIT 不直接等于泄漏 |
| 服务 | 请求率、错误率、p95/p99、队列深度 | SLO 预警或错误预算加速消耗 | SLO 中断或错误预算快速燃尽 | 基础设施正常不代表服务正常 |

#### 2.3 工具链与命令用途

| 工具或命令 | 主要用途 | 使用约束 |
| --- | --- | --- |
| `uptime`、`top -H`、`mpstat -P ALL 1` | 负载、线程和单核利用率 | 先确认逻辑核、容器视图与采样窗口 |
| `pidstat -u -w -r -d 1` | 进程 CPU、切换、内存和 I/O 随时间变化 | 配合具体 PID 与时间范围留存 |
| `vmstat 1`、`free -h` | 运行队列、换页、内存与块 I/O 概览 | 首行常为启动以来均值，重点看后续采样 |
| `/proc/pressure/*` | CPU、memory、I/O 的 PSI 停顿 | 同时看 some/full 及总量，容器支持依版本 |
| `iostat -xz 1`、`sar` | 设备延迟、队列、吞吐和历史趋势 | util 在 NVMe/并发热备上不等于百分百瓶颈 |
| `ss -lntup`、`ss -ti`、`nstat -az` | 监听、连接详情和协议计数器 | 使用差值而非累计总量判故障 |
| `ethtool -S`、`ip -s link` | 网卡驱动计数与链路错误 | 计数名称依驱动，先清零基线或取增量 |
| `lsof`、`/proc/<pid>/fd` | 文件和 socket 泄漏、打开路径 | 与进程及命名空间权限相匹配 |
| `perf top/record/report` | CPU 采样、热点函数和调用栈 | 安装匹配符号，限制采样频率与时长 |
| `strace -f -tt -T -p <pid>` | 系统调用序列、错误和耗时 | 高开销，不长期跟踪生产高 QPS 进程 |
| `numastat`、`numactl --hardware` | NUMA 命中、节点内存和拓扑 | 与线程、设备 NUMA 位置联合分析 |
| BCC/bpftrace `runqlat`、`offcputime`、`biolatency` | eBPF 调度延迟、阻塞栈和块 I/O 延迟 | 先验证内核 BTF、权限和工具开销 |
| `execsnoop`、`opensnoop`、`tcplife`、`profile` | 短进程、文件打开、连接周期和火焰图采样 | 使用精确过滤，不采集敏感参数或载荷 |

#### 2.4 常用内核参数调整清单

- 仅通过配置管理和 `/etc/sysctl.d/*.conf` 持久化，先运行 `sysctl --system` 校验，再逐项应用并记录旧值；容器内参数还须确认是否 namespaced。
- 下列值是常见起点而非通用最优值；标为“条件”的项目必须由监控或产品文档证明需要，未使用 conntrack 时不调整对应项。

| 参数 | 建议起点 | 风险与适用条件 |
| --- | --- | --- |
| `fs.file-max=1048576` | 大连接主机可按容量提高 | 仅提高系统上限，仍须设置进程 `LimitNOFILE`；过大可能掩盖泄漏 |
| `net.core.somaxconn=4096` | 高并发监听服务 | 应用 backlog 同步调整；不能修复 accept 处理缓慢 |
| `net.ipv4.tcp_max_syn_backlog=8192` | 已确认 SYN 队列溢出 | 增加内存占用，不能代替 DDoS 防护 |
| `net.ipv4.tcp_syncookies=1` | 默认保持开启 | SYN flood 下为兜底，不应关闭常规队列监控 |
| `net.core.netdev_max_backlog=8192` | 条件：入口包积压且队列丢弃 | 增加排队与内存，先检查 RSS、软中断和网卡队列 |
| `net.ipv4.tcp_keepalive_time=600` | 长连接需较快探活 | 只是 TCP 探活，应用心跳仍必要 |
| `net.ipv4.tcp_keepalive_intvl=30` | 与上项配套 | 过短会放大空闲连接报文量 |
| `net.ipv4.tcp_keepalive_probes=5` | 与上项配套 | 按可接受故障发现时间计算总窗口 |
| `net.ipv4.ip_local_port_range="10240 65535"` | 条件：出向五元组确实耗尽 | 先避开本地监听端口并优先复用连接 |
| `net.netfilter.nf_conntrack_max=262144` | 条件：启用 conntrack 且容量不足 | 每项占内核内存，须结合条目数和哈希表计算 |
| `vm.max_map_count=262144` | 条件：搜索、数据库等产品要求 | 提高映射数量上限，不等于增加可用内存 |
| `vm.swappiness=10` | 条件：已证明过度换出且需降低倾向 | 不关闭 swap，不保证不换页；数据库按官方建议设置 |
| `net.ipv4.tcp_mtu_probing=1` | 条件：确认 PMTUD 黑洞且无法立即修复网络 | 属缓解措施，不能替代 MTU/ICMP 根因修复 |

- 默认不修改 TCP 读写缓冲自动调优、拥塞控制、调度器粒度、dirty 比例和 overcommit；确需修改时按内存大小、带宽时延积和应用持久性专项计算。
- 禁止启用已移除或曾导致 NAT 连接问题的 `tcp_tw_recycle`，禁止为“优化”关闭 TCP timestamps、随机降低 TIME_WAIT 语义或全局 `echo 3 > drop_caches`。
- `vm.overcommit_memory=1`、禁用 THP、静态 HugeTLB、Redis 相关设置均按产品要求独立评审；`panic_on_oom`、自动重启内核和强制 OOM 策略不得作为容量方案。

#### 2.5 调优验收与回退

- 每次参数变更记录对象、旧值、新值、依据、审批人、生效范围、观察窗口和回退命令，并纳入主机或镜像配置版本。
- 验收至少包含相同负载下的吞吐、p50/p95/p99、错误率、CPU、内存、I/O 和下游影响；性能提升但破坏持久性、隔离或公平性视为失败。
- 压测需含稳态、突发、慢下游、重连和故障恢复阶段；达到瓶颈时确认瓶颈所在，不把客户端打满误判为服务端容量。
- 生产变更采用单实例或小比例灰度；出现 SLO 退化、资源异常或错误预算加速立即回退，不以“继续观察”拖延止损。

### 3. 服务部署最佳方案

#### 3.1 Linux 发行版、架构与文件系统选择

- 选择仍处于厂商安全支持期的企业发行版或稳定发行版，统一内核、libc、CPU 架构和镜像构建来源；不得新增已 EOL 或仅有个人维护的系统。
- 发行版选择依次评估商业支持、安全更新、硬件驱动、容器/K8s 兼容性、团队运维能力和软件认证，不以短期基准跑分作为首要依据。
- 生产使用最小化镜像和受控软件源，版本升级采用不可变镜像或经过验证的事务化流程；跨大版本升级先重建验证，不在业务高峰原地赌博式升级。
- 通用数据盘优先 XFS 或 ext4：XFS 适合大文件、高并发和在线扩容，ext4 适合通用根盘及成熟运维场景；最终服从数据库和云平台认证矩阵。
- ZFS 适用于需要校验、快照、压缩和自管理的场景，但须专项规划 ARC、vdev、 scrub 和内存；Btrfs 等仅在团队具备恢复经验且产品支持时使用。
- 根分区、日志、数据和备份按故障与容量隔离；挂载使用 UUID 或稳定设备标识，敏感目录按需设置 `nodev/nosuid/noexec`，禁止对应用必需目录机械加 `noexec`。
- 云盘明确 IOPS、吞吐、突发信用和多可用区复制边界；本地 NVMe 仅在有副本、备份和节点丢失预案时承载持久数据。

#### 3.2 系统初始化基线

- 主机名、IP、DNS、路由、MTU 和资产标签通过自动化生成；内部 DNS 至少双节点，禁止把公共 DNS 作为内部服务发现的唯一依赖。
- 系统日志统一 UTC，业务可按约定展示本地时区；使用 `chrony` 对接至少两个可信时间源，检查 `chronyc tracking/sources`，禁止用定时 `ntpdate` 大幅跳时。
- OpenSSH 使用密钥或集中身份认证，禁止 root 直接远程密码登录；`PasswordAuthentication no`、`KbdInteractiveAuthentication no` 在替代认证验证后启用，配置变更先 `sshd -t`。
- SSH 限制来源和允许组，管理流量经堡垒机或受控管理网；重载时保留已验证会话并具备带外回退，禁止未测试即关闭唯一访问通道。
- 每人独立账号，服务使用不可登录的专用账号；sudo 按命令和角色最小授权，特权操作审计，禁止通用 `NOPASSWD: ALL` 和多人共用账号。
- 防火墙默认拒绝入站、仅开放必要端口和来源，云安全组与主机防火墙职责明确；管理端口不对全网开放。
- `umask` 默认 027 或按应用评审；秘密文件由专用系统注入并限制所有者、权限和挂载范围，不写入镜像、命令行、环境快照或日志。
- shell 的 `ulimit` 不管理 systemd 服务；在服务单元设置 `LimitNOFILE`，并检查 `/proc/<pid>/limits`，进程线程数还受 `LimitNPROC`、cgroup PIDs 与内核上限共同约束。
- 启用 SELinux 或 AppArmor  enforcing，禁止以永久关闭 MAC 解决权限问题；auditd 记录特权、账号、关键配置和安全策略变更。
- journald 设置持久化、磁盘上限和转发；文本日志配置 logrotate 的 `daily/size`、`rotate`、`compress`、`delaycompress`、`missingok`、`notifempty` 及正确 reload/copytruncate 策略。
- 仅安装必要软件，关闭未使用服务；安全补丁有固定窗口、例外审批和内核重启计划，自动升级不得绕过业务健康检查。
- 初始化由 Ansible 等幂等配置管理执行，完成 `sshd -t`、`sysctl --system`、`nginx -t`、挂载和时间同步检查后方可接入流量。

#### 3.3 systemd 服务单元标准

- 每个常驻服务由独立 unit 管理，配置置于 `/etc/systemd/system/<name>.service.d/override.conf`，避免直接修改软件包原文件。
- 服务优先 `Type=simple` 或 `notify`；只有程序确实按协议通知就绪才使用 `notify`，禁止用 `Type=forking` 包装不退出前台的进程。
- 使用独立 `User/Group`，工作目录、环境和配置显式声明；秘密通过 `LoadCredential` 或受控文件注入，不在可广泛读取的 unit 中明文保存。
- 标准模板如下，资源值必须按容量评测替换：

```ini
[Unit]
Description=example application
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=60
StartLimitBurst=5

[Service]
Type=simple
User=app
Group=app
WorkingDirectory=/opt/app
EnvironmentFile=-/etc/app/app.env
ExecStart=/opt/app/bin/server --config /etc/app/config.yaml
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5s
TimeoutStartSec=60s
TimeoutStopSec=45s
KillSignal=SIGTERM
SuccessExitStatus=0 143
LimitNOFILE=65536
LimitNPROC=4096
MemoryMax=2G
TasksMax=4096
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/app /var/log/app

[Install]
WantedBy=multi-user.target
```

- `Restart=on-failure` 不替代健康检查；退出码、OOM、信号和重启风暴必须告警，`Restart=always` 仅在语义明确且依赖恢复机制完备时使用。
- `After` 只定义顺序，不保证依赖可用；需要网络在线时配合 `network-online.target`，应用仍需对数据库和 DNS 实施连接重试、超时与退避。
- `MemoryMax` 过低会触发 OOM，过高失去保护；磁盘写目录须列入 `ReadWritePaths`，额外 capability 用 `CapabilityBoundingSet` 最小化。
- 标准输出进入 journald 并附加服务、环境、版本标签；高日志量设置速率与总量控制，结构化字段由应用输出，禁止用重启服务解决日志写满。
- 变更后执行 `systemd-analyze verify`、`systemctl daemon-reload`、启动与状态检查；用 `systemctl cat/show` 核对最终合并值，用 `journalctl -u` 验证启动和停止原因。
- 应用处理 SIGTERM、停止监听并排空在途请求；`TimeoutStopSec` 覆盖最慢正常请求，超时强杀必须纳入数据一致性评审。

#### 3.4 二进制、容器与裸机部署取舍

| 方式 | 适用场景 | 必备控制 | 不宜采用的情形 |
| --- | --- | --- | --- |
| 裸机进程/二进制 | 少节点、强硬件依赖、简单常驻服务 | systemd、版本目录、原子切换、配置管理和回滚包 | 依赖冲突严重、弹性频繁或交付环境不一致 |
| 系统包管理 | 发行版原生组件和基础中间件 | 受控仓库、版本锁定、签名验证、升级窗口 | 需要同一主机多版本并存且包互相冲突 |
| 单节点容器 | 统一依赖和交付、边界清晰的服务 | 固定 digest、非 root、资源限制、日志和持久卷 | 把 `docker run` 当高可用，或数据卷生命周期无人管理 |
| K8s 容器平台 | 多服务、弹性、标准发布和故障自愈 | 完整准入、资源治理、网络策略、可观测和备份 | 团队无平台能力、单服务成本过高或硬件不兼容 |
| 虚拟机强隔离 | 多租户、高安全边界、特殊内核 | 镜像基线、补丁、资源超分控制和快照备份 | 仅为避免镜像治理而增加长期运维层 |

- 二进制发布采用 `/opt/app/releases/<version>`、`current` 原子软链和共享数据目录；配置、程序和数据分离，回滚切回已验证产物而非现场重新编译。
- 容器镜像采用多阶段构建、最小基础镜像和不可变 digest，生成 SBOM、漏洞扫描和签名；禁止 `latest` 进入生产清单。
- 所有方式均需明确健康检查、停止语义、资源上限、日志、备份、升级兼容与回滚，容器化不自动解决这些问题。

#### 3.5 Nginx 反向代理规范

- `worker_processes auto` 为起点，worker 数、连接数和 `worker_rlimit_nofile` 与内存及 FD 上限匹配；不得在事件循环前增加无依据的 worker 数量。
- upstream 启用长连接，`proxy_http_version 1.1` 并清空 `Connection`；keepalive 连接池结合上游并发和连接复用率设置，避免连接耗尽。
- 明确 `proxy_connect_timeout`、`proxy_read_timeout`、`proxy_send_timeout`、客户端请求体、头部和缓冲区上限；SSE、WebSocket、上传和长轮询单独设置。
- `proxy_next_upstream` 仅对幂等请求开放，限制错误类型、次数和总耗时；非幂等请求重试必须由唯一请求键和应用语义保证。
- 保留规范 Host，按信任边界设置 `X-Forwarded-For/X-Forwarded-Proto`；`real_ip` 只信任明确代理网段，不得直接信任客户端伪造头。
- 访问日志使用 JSON，包含 request_id、状态、字节数、请求耗时、upstream 地址、upstream 状态及连接/首字节/总耗时，不记录 Cookie、Authorization 和敏感查询参数。
- TLS 1.2/1.3，私钥最小权限，证书自动续期并提前 30/14/7 天告警；OCSP stapling、HSTS 和 HTTP/2/3 按域名、客户端及网络验证后启用。
- 开源 Nginx 被动故障摘除不等于主动健康检查；需要主动探测时使用外部控制面或支持该能力的版本，摘除与恢复均设连续成功/失败阈值。
- 发布前执行 `nginx -t`，采用 reload 平滑加载并验证旧 worker 退出；`proxy_buffering`、缓存和限流按端点配置，避免错误缓存个性化响应。
- 静态压缩优先预压缩或按需开启，已经压缩的媒体不重复压缩；缓存键包含必要维度并防止未净化请求头造成缓存污染。

#### 3.6 HAProxy 反向代理规范

- 四层 TCP 转发用于无法终止 TLS 或仅按连接路由的场景，七层 HTTP 用于路径、头部、灰度和内容治理；选择后保持超时、日志和后端语义一致。
- 全局、frontend、backend、listen 的 `maxconn` 分层设置，后端 server `maxconn` 小于应用真实容量；排队必须有 `timeout queue` 和队列深度告警。
- 显式配置 `timeout connect/client/server/http-request/http-keep-alive/queue/tunnel`，避免默认无超时造成连接悬挂；WebSocket 与长连接使用匹配的 tunnel 超时。
- `option httpchk` 指定专用健康端点，`check inter/fall/rise` 控制探测频率和抖动；健康检查不得触发重事务或依赖所有下游同时健康。
- 默认无状态服务采用 roundrobin 或 leastconn，长请求差异大优先 leastconn；只有缓存局部性或会话需要时使用一致性哈希/粘性，不把粘性当会话持久化。
- `retries` 和 `option redispatch` 只配合幂等语义及总重试预算，故障时防止重试风暴；慢启动用于后端恢复，摘除须先停止新连接并排空。
- 多实例的限流 stick-table 需 peers 同步或接受本地计数语义；stats socket/页面限制到管理网并认证，运行时修改必须同步持久配置。
- reload 前使用 `haproxy -c -f` 校验，采用 systemd/无缝重载机制保持存量连接；日志包含前端、后端、服务器、终止状态、队列和各阶段计时。

#### 3.7 MySQL、PostgreSQL 与 Redis 部署基线

- 通用：只运行厂商支持的版本，主备跨故障域，数据盘与备份隔离；默认 UTC、专用账号、最小授权、TLS、审计、慢查询与容量告警。
- 通用：生产不开放公网，连接经池化并设上限；持久化、复制延迟、备份和 PITR 定期演练，高可用切换不等于备份。
- MySQL 默认 InnoDB、utf8mb4 和 GTID 复制；强持久场景保持 `sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`，若放宽须量化断电丢失窗口并审批。
- MySQL 独占实例的 buffer pool 可从物理内存 60%～70% 起步并扣除连接、系统与代理开销；redo、临时表和连接内存按峰值工作负载验证。
- MySQL binlog 使用 ROW，开启慢查询日志并设置保留和脱敏；副本只读、监控复制延迟与 GTID 缺口，备份同时验证全量、binlog 和一致性位点。
- PostgreSQL `shared_buffers` 可从内存约 25% 起步，`effective_cache_size` 只是规划器估计；`work_mem` 按每个排序/哈希节点消耗，禁止按连接数直接全局放大。
- PostgreSQL 保持 `fsync=on`、`full_page_writes=on`，需要副本时 `wal_level=replica`；连接数保持适度并配合池化，避免用数千直连解决等待。
- PostgreSQL 归档 WAL 以支持 PITR，按 WAL 速率设置 checkpoint 和 `max_wal_size`；autovacuum 默认开启并按大表调整，监控膨胀、事务年龄和复制槽保留。
- PostgreSQL 使用 `pg_stat_statements`、checkpoint/锁等待日志定位问题；物理复制、逻辑复制和备份的恢复目标分别验证。
- Redis 绑定私网并启用 protected mode、ACL，跨不可信网络启用 TLS；必须显式设置 `maxmemory` 和驱逐策略，为碎片、复制缓冲和 fork 预留内存。
- Redis 持久化按 RPO 选择 AOF `everysec` 与 RDB 组合，持久目录使用可靠磁盘；禁用持久化或仅以副本代替备份须明确数据可丢失。
- Redis 高可用采用至少三个跨故障域 Sentinel 或 Cluster 主从拓扑，故障切换 quorum/多数派与客户端发现同时验证；不把双节点多数派当可靠仲裁。
- Redis 按官方文档处理 `vm.overcommit_memory` 和 THP，监控 `used_memory_rss`、碎片率、驱逐、拒绝连接、慢日志、延迟和复制积压；大 key 与热 key 设置治理门槛。

#### 3.8 消息队列与中间件部署要点

- 新 Kafka 集群使用受支持的 KRaft 模式，控制器与 broker 角色按规模隔离；关键 topic `replication.factor>=3`、`min.insync.replicas=2`，生产端 `acks=all` 并启用幂等。
- Kafka 禁止 `unclean.leader.election.enable=true` 作为可用性捷径；分区数按目标吞吐、单分区能力和消费者并行度计算，预留 controller、ISR、副本同步与磁盘水位告警。
- Kafka broker 跨机架/可用区分布，副本分配避免同域；保留期同时受时间和容量约束，监控 under-replicated/offline partitions、请求延迟、consumer lag 和重平衡。
- RabbitMQ 关键队列使用 quorum queue，三或五个节点跨故障域；队列 durable、消息 persistent、publisher confirm 和消费者手动 ack 按可靠性语义组合。
- RabbitMQ 设置 consumer prefetch、单条处理超时、重试上限和死信策略，禁止无限重投；内存/磁盘 alarm 不得关闭，连接、channel、未确认消息和队列增长必须告警。
- MQ 的“至少一次”要求消费者幂等和去重；顺序、延迟、事务和过期语义按产品验证，禁止把消息持久化误认为端到端绝不重复或绝不丢失。
- 中间件统一执行版本支持检查、配置校验、容量水位、TLS/ACL、备份恢复和滚动升级预演；管理 UI 不暴露公网，默认账号和示例配置必须移除。
- Elasticsearch 等搜索中间件需独立规划堆外内存、分片、快照和多数派发现；ZooKeeper 等协调系统采用奇数节点、独立低延迟磁盘并监控 quorum，不与高负载业务争抢资源。

#### 3.9 Kubernetes 生产部署规范

- 使用仍处于社区或厂商支持期的版本，控制平面升级遵守版本偏差；生产控制平面/etcd 采用三或五个跨故障域成员，并定期验证 etcd 快照恢复。
- Namespace 配置 ResourceQuota、LimitRange 和默认拒绝 NetworkPolicy；RBAC 按 ServiceAccount 最小授权，非必要不自动挂载 token，禁止默认 sa 绑定集群管理权限。
- 工作负载固定镜像 digest，禁止使用 `latest`；配置与秘密分离，秘密通过受控 Secret/KMS/外部秘密系统注入并启用静态加密和轮换。
- Pod 默认 `runAsNonRoot`、只读根文件系统、`allowPrivilegeEscalation=false`、drop `ALL` capability、`seccompProfile=RuntimeDefault`；hostPath、hostNetwork、hostPID 和 privileged 需专项审批。
- CPU requests 以稳态 p95 与峰值并行度为依据，memory requests 以真实工作集加余量为依据；关键服务保证至少两个副本，跨可用区和节点反亲和/拓扑分布。
- 内存 limits 必须防止无限增长并高于正常峰值；CPU limits 是否设置结合 throttling 和 SLO，延迟敏感的独占型服务可令 requests=limits 获得 Guaranteed QoS。
- HPA 至少 `minReplicas=2`，按 CPU、自定义或外部指标选择真正代表饱和度的指标；设置缩容稳定窗口和 `behavior`，避免指标尖峰导致振荡。
- HPA 与 VPA 不得在同一 CPU/内存指标上互相打架；I/O 密集型、连接数型或队列型服务优先使用队列延迟、并发数或 lag，而非只看 CPU。
- PDB 用于限制滚动升级等自愿中断，不能预防节点同时故障；副本数和 PDB 必须允许任一可用区维护，控制器升级前检查 `disruptionsAllowed`。
- startupProbe 保护慢启动，readinessProbe 决定摘流，livenessProbe 仅判断无法自愈的本地故障；探针轻量且独立，禁止因单个共享下游短暂故障导致全组重启。
- Deployment 常规采用 `maxUnavailable=0`、`maxSurge=25%` 起步，设置 `minReadySeconds`、合理 `progressDeadlineSeconds`；单写状态服务评估 Recreate 或 StatefulSet。
- 收到 SIGTERM 后停止就绪、停止接流、处理在途请求并关闭连接，`terminationGracePeriodSeconds` 覆盖正常排空；preStop 只是辅助，不替代应用优雅停止。
- 回滚优先 Git revert 并重新走流水线，保留足够 ReplicaSet revision；数据库采用向后兼容的 expand—migrate—contract，避免回滚代码无法读取新数据。
- 节点保留 N+1 故障容量，系统组件和业务资源隔离；StorageClass、卷扩展、快照、回收策略和可用区绑定经过恢复测试。
- 准入策略阻断特权、未知仓库、缺少 requests/内存 limit/探针/所有者或缺少网络策略的工作负载；集群、控制器、apiserver、etcd、DNS、Ingress 与节点指标统一告警。

#### 3.10 CI/CD 流水线与质量门禁

- 流水线阶段固定为：提交校验→构建与单元测试→安全扫描→不可变制品→预发部署与集成验证→生产审批→渐进发布→发布后验证与归档。
- 提交阶段执行格式、静态检查、依赖锁定、单元测试和配置 schema 校验；所有必需测试通过才可合并，失败禁止通过人工重跑掩盖不稳定测试。
- 安全阶段执行 SAST、秘密扫描、SCA、镜像/IaC 扫描、许可证检查和 SBOM；禁止新增明文凭据及未豁免的严重漏洞，例外须有负责人、补偿控制和到期日。
- 构建阶段产出带 commit、版本和校验和的不可变制品，保存构建来源与签名；同一 digest 晋级各环境，禁止生产重新构建不同代码。
- 部署前执行数据库迁移演练、配置差异、容量和兼容性门禁；K8s 清单经过策略校验，Nginx/HAProxy/systemd 配置先运行各自语法检查。
- CI 使用 OIDC 等短期身份和最小权限，秘密不落日志；构建依赖和基础镜像来自批准仓库，发布与回滚权限分离并保留审计。
- 覆盖率采用“核心路径必覆盖、变更代码覆盖率不下降”等可持续门禁，不用单一高覆盖率替代断言质量；性能门禁比较同环境的延迟、吞吐和资源回归。
- 生产发布需经过授权审批和变更单关联，自动验证健康、错误率、延迟和关键业务指标；门禁失败自动停止扩大流量并触发回退。
- 流水线保存测试报告、扫描结果、审批、制品 digest、部署版本和回滚结果，满足审计追溯；环境差异只能来自受控配置和秘密。

#### 3.11 蓝绿、金丝雀与回滚判据

- 蓝绿适用于两套完整环境、共享或兼容数据层且需快速切流的场景；切换前确认绿环境容量、配置、缓存预热、健康检查和后台任务唯一性。
- 蓝绿切换后保留蓝环境只读或停止写入的明确状态；发生新写入后回滚必须处理数据分叉，不能把 DNS/负载均衡切回当作完整数据回滚。
- 金丝雀要求新旧版本可并行、调用可观测、流量可精确控制、数据库前后兼容且容量足够；不具备这些条件时先改造，不强行灰度。
- 流量阶梯可从 1%→5%→25%→50%→100% 起步，每级覆盖足够请求量和业务时段；高流量服务按样本量，低流量服务按完整业务周期，不机械等待固定分钟数。
- 金丝雀组与对照组排除版本以外变量，比较错误率、p95/p99、饱和度、日志异常和关键业务转化；任一突破预设绝对阈值或显著劣于基线即停止。
- 自动回滚触发至少包括：核心健康检查连续失败、错误预算快速燃尽、p99 超 SLO、资源失控、数据一致性异常或安全策略失败。
- 发布前验证回滚包、配置、数据库兼容和依赖版本，定期实际演练；回滚后仍保留现场指标和审计，不以服务恢复代替原因闭环。
- 定时任务、消费者和批处理需防止蓝绿双跑，可采用单领导者、分区流量或显式暂停；消息格式与事件 schema 必须支持新旧消费者交错处理。

### 4. 可观测性与运维标准

#### 4.1 日志规范

- 应用日志采用单行 JSON，必填 UTC RFC3339 时间、level、service、environment、version、instance、event、message；请求链路附 trace_id、span_id、request_id。
- ERROR 必须包含稳定错误码、错误类型和必要堆栈，上下文只保留可定位字段；禁止记录口令、令牌、私钥、完整证件号、银行卡、Cookie、Authorization 和未脱敏载荷。
- 容器写 stdout/stderr，由采集器转发；裸机优先 journald 或受控文件，应用不得自行多点争抢轮转，采集端必须处理背压、磁盘缓冲和断点续传。
- 日志级别可动态调整且限时恢复；高频循环先采样或聚合，ERROR 不盲目全量重复打印，关键安全审计不得被采样丢失。
- 集中日志按安全与业务要求设置热、温、冷保留期、访问控制和完整性保护；上线前验证按服务、版本、trace_id 和时间检索的能力。

#### 4.2 指标与链路规范

- 指标同时覆盖 USE、RED 和四个黄金信号，业务 SLO 用明确事件定义；Prometheus 命名带单位，标签使用固定低基数值，禁止 user_id、URL 原文和 request_id 作为标签。
- 延迟使用直方图或摘要并配置与 SLO 对齐的桶；p99 必须有足够样本，实例重启正确处理 counter，rate 窗口至少覆盖多个抓取周期。
- node、进程、容器、数据库、MQ、负载均衡和 K8s 组件均有 exporter 与自监控；采集目标失联、规则加载失败、远程写堆积和存储容量本身必须告警。
- 链路统一 OpenTelemetry 与 W3C Trace Context，入口生成或校验 traceparent，跨 HTTP、消息和异步任务传播；baggage 不放秘密或高基数字段。
- Span 名称低基数，属性包含协议、服务、结果和必要拓扑信息；数据库与消息语句按规范脱敏，采样异常和慢调用优先保留，并评估 tail sampling 的资源成本。
- 日志、指标和链路使用一致的 service.name、deployment.environment、version 与实例标识，仪表盘可直接跳转对应 trace 和发布版本。

#### 4.3 告警分级与值班

| 级别 | 判定 | 响应与升级 | 通知方式 |
| --- | --- | --- | --- |
| P1 | 核心业务大面积不可用、数据丢失或重大安全事件 | 5 分钟内响应，立即拉通事件指挥，15 分钟未响应升级 | 电话/强提醒并同步事件频道 |
| P2 | 核心功能显著退化、冗余丧失或错误预算快速消耗 | 15 分钟内响应，30 分钟未缓解升级 | 值班强提醒与电话兜底 |
| P3 | 局部功能异常、有绕行或容量趋势风险 | 工作时段 1 小时内处理并纳入工单 | 工单与团队频道 |
| P4 | 优化建议、低风险趋势和信息通知 | 例行处理，不触发夜间值班 | 工单或日报 |

- 告警优先基于用户症状和 SLO，多窗口、多燃尽率抑制短暂噪声；资源原因告警用于补充诊断，避免同一故障数百条重复呼叫。
- 每条告警必须有负责人、仪表盘、运行手册、影响、止血和升级路径；无动作价值的告警删除，长期静默须审批和到期时间。
- 值班实行主备交接，确认未解决事件、变更、容量风险和静默；P1/P2 结束后完成时间线、根因、影响、修复与行动项复盘，禁止只追责个人。
- 定期注入测试告警验证路由、电话、升级和值班可用性；监控平台自身跨故障域，避免与所监控业务同时失效。

#### 4.4 备份策略与恢复演练

- 按业务确定 RPO/RTO、保留周期和一致性边界，采用 3-2-1-1-0：至少三份、两种介质、一份异地、一份离线或不可变、恢复校验零错误。
- 数据库执行全量/增量与日志连续归档：MySQL 保留一致全量和 binlog，PostgreSQL 保留基础备份和 WAL，Redis 明确 RDB/AOF 的丢失窗口。
- 备份加密、独立身份、最小删除权限和跨账号/故障域保存；备份与生产管理员权限隔离，防勒索策略包含不可变保留和删除告警。
- 每次备份自动校验完成状态、大小异常、日志连续性和保留清理；仅有“任务成功”不能证明可恢复，必须定期在隔离环境实际恢复并运行数据校验。
- 至少每季度执行关键系统恢复演练，每年执行跨故障域灾难恢复演练；记录实测 RPO/RTO、依赖顺序、DNS/证书/秘密恢复和缺口整改。
- K8s 同时备份声明式配置和持久数据，etcd 快照不能替代业务卷备份；恢复演练包含集群版本、CRD、存储类和外部依赖兼容。

#### 4.5 变更管理与回滚

- 变更单必须包含目的、范围、风险、依赖、配置差异、验证、回滚、负责人和通知对象；生产禁止未审计的临时手工改动。
- 按只读/可逆、低风险、高风险和数据变更分级审批；高风险变更安排维护窗口、业务确认、双人复核和带外访问，紧急变更事后补齐审计。
- 基础设施通过 IaC 和配置管理实施，计划输出经审查后应用；漂移定期检测，控制台应急修改必须回写代码。
- 数据库变更优先在线、分阶段、向后兼容，大表迁移先评估锁、复制延迟、磁盘和回滚； destructive change 延迟到旧版本全部退出后执行。
- 回滚判据在变更前量化并自动或半自动执行，回退包含程序、配置、代理、任务和数据的完整状态；变更后经过约定观察期才关闭工单。
- 配置、制品、仪表和运行手册同步版本化；故障止血后补做根因分析和永久修复，临时权限、跳过门禁和手工参数不得长期遗留。

- [ ] 9. root 远程直登已禁止，SSH 密钥/集中认证生效，密码认证关闭前已验证替代通道和带外回退。

- [ ] 18. 服务仅监听设计地址与端口，无多余进程和示例应用；端口、进程和配置与资产清单一致。
- [ ] 19. 应用制品版本、digest、签名、SBOM 和来源可追溯，生产未使用 `latest`、现场编译或无法回滚的临时文件。
- [ ] 20. 健康检查区分启动、就绪和存活，探针不制造依赖级联；停止流量后在途请求可在规定时间排空。
- [ ] 21. Nginx/HAProxy 配置语法检查通过，代理超时、上传限制、真实 IP、上游长连接、日志和重试语义符合规范。
- [ ] 22. TLS 证书链、主机名、协议和私钥权限正确，自动续期已测试，30/14/7 天到期告警可达值班组。
- [ ] 23. 数据库/MQ 的持久化、复制、仲裁、连接上限、账号、TLS、容量水位和故障切换均通过上线验证。
- [ ] 24. CPU、内存、磁盘、网络和下游完成容量压测，保留峰值余量；p95/p99、错误率和资源基线已归档。
- [ ] 25. 发布流水线测试与安全门禁通过，蓝绿/金丝雀或滚动策略已配置，旧制品和配置可在一键流程内回退。

#### 5.4 可观测、备份与交接

- [ ] 26. JSON 日志包含服务、环境、版本和链路标识，敏感字段已脱敏，集中检索可查到本机启动与请求日志。
- [ ] 27. journald/logrotate 的轮转、压缩、保留、磁盘上限和采集背压已验证，日志写满不会挤占根分区。
- [ ] 28. 节点、进程、容器及中间件指标已采集，SLO 仪表盘、告警规则、去重、静默到期和值班路由均实测。
- [ ] 29. OpenTelemetry 链路能从入口追踪到服务与关键下游，trace_id 可关联日志，采样不会泄露敏感属性。
- [ ] 30. 备份任务、加密、异地/不可变副本和保留策略已启用，并完成一次隔离环境真实恢复与数据一致性校验。
- [ ] 31. 磁盘空间/inode、内存/OOM、CPU 限流、服务退出、证书、备份和硬件故障告警已逐项触发并确认响应人。
- [ ] 32. 运行手册、架构图、依赖清单、仪表盘、值班表、变更单、回滚步骤和带外访问已完成交接并获准接流。

## 第三篇 安全环境标准规范与处理方法

> 版本基准：2026 年 11 月。本文规定通用控制基线；行业监管、合同约定或系统定级要求更严格时，从其要求。标准引用以现行有效版本为准，实施前应复核标准状态。

### 1. 中国合规体系

#### 1.1 《网络安全法》关键义务

- 采用 2025 年修正、2026 年 1 月 1 日起施行的《中华人民共和国网络安全法》，建立覆盖建设、运营、维护和使用的责任体系。[cite:1]
- 落实网络安全等级保护：制定内部制度和操作规程，明确安全负责人，落实访问控制、防恶意代码、防攻击侵入等技术措施。
- 监测并记录网络运行状态和安全事件，相关网络日志依法留存不少于六个月；执行数据分类、重要数据备份和加密。
- 建设网络安全防护能力时同步规划、同步建设、同步使用；采购网络关键设备和网络安全专用产品时核验适用的认证、检测要求。
- 制定网络安全事件应急预案，及时处置漏洞、病毒、攻击和侵入；事件发生立即启动预案、采取补救措施并依法报告。
- 关键信息基础设施运营者还须落实专门机构、人员背景审查、教育培训、容灾备份、定期演练、采购安全审查及年度检测评估等义务。

#### 1.2 《数据安全法》关键义务

- 依据 2021 年《中华人民共和国数据安全法》建立全流程数据安全管理制度，开展教育培训并配置必要技术措施；联网数据处理同时落实等级保护义务。[cite:2]
- 按数据重要程度及泄露、篡改、破坏、非法获取或利用后的危害实施分类分级；识别重要数据和国家核心数据并执行相应保护制度。
- 重要数据处理者明确数据安全负责人和管理机构，定期开展数据处理活动风险评估，并按规定向主管部门报送报告。
- 持续开展风险监测；发现缺陷、漏洞立即补救，发生事件立即处置，依法及时告知用户并报告主管部门。
- 数据收集、使用限于合法、正当方式和规定目的范围；委托处理、共同处理、对外提供及公开前执行审批、合同约束和接收方风险评估。
- 《网络数据安全管理条例》（2024 年公布，2025 年 1 月 1 日施行）进一步要求重要数据处理者每年度开展风险评估；重要数据提供、委托处理或共同处理前进行风险评估。[cite:4]

#### 1.3 《个人信息保护法》关键义务

- 依据 2021 年《中华人民共和国个人信息保护法》，逐项记录处理目的、方式、信息种类、保存期限和第十三条规定的合法性基础，不得将“同意”视为唯一合法性基础。[cite:3]
- 遵循合法、正当、必要、诚信、公开透明和最小范围原则；不得过度收集，不得以拒绝非必要个人信息处理为由拒绝提供基本业务功能。
- 履行显著、清晰、完整的告知义务；处理敏感个人信息须具有特定目的和充分必要性，采取严格保护措施并依法取得单独同意。
- 向其他处理者提供、公开个人信息或向境外提供个人信息时，依法履行专门告知和单独同意等要求；不满十四周岁未成年人信息按敏感个人信息保护并取得监护人同意。
- 建立查阅、复制、更正、补充、删除、限制或拒绝处理、撤回同意及注销账户的处理流程，验证申请人身份并在法定条件下及时响应。
- 委托处理须约定目的、期限、方式、种类、保护措施和双方权利义务并监督受托人；不得仅凭供应商承诺转移处理者责任。
- 对敏感个人信息、自动化决策、委托处理、对外提供、公开及跨境等法定场景事前开展个人信息保护影响评估并留存记录；定期实施合规审计。
- 达到规定数量的处理者指定并报送个人信息保护负责人；境外处理者依法在境内设立专门机构或指定代表。
- 发生或可能发生泄露、篡改、丢失时立即补救并通知主管部门和个人；依法可不通知个人的情形须留存依据，主管部门要求通知时仍应执行。
- 个人信息跨境前判定安全评估、保护认证、标准合同或法定豁免路径，并结合 2024 年《促进和规范数据跨境流动规定》复核，不得沿用失效门槛或豁免结论。[cite:26]

#### 1.4 网络安全等级保护 2.0

- 定级采用 **GB/T 22240-2020《信息安全技术 网络安全等级保护定级指南》**；基本控制采用 **GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》**，该版本经 2025 年复审继续有效。[cite:5][cite:6]

| 等级 | 对象受破坏后的影响判定摘要 |
| --- | --- |
| 第一级 | 对公民、法人和其他组织合法权益造成一般损害，但不危害国家安全、社会秩序和公共利益。 |
| 第二级 | 对相关合法权益造成严重或特别严重损害，或危害社会秩序和公共利益，但不危害国家安全。 |
| 第三级 | 对社会秩序和公共利益造成严重危害，或对国家安全造成危害。 |
| 第四级 | 对社会秩序和公共利益造成特别严重危害，或对国家安全造成严重危害。 |
| 第五级 | 对国家安全造成特别严重危害。 |

- 定级对象包括网络基础设施、信息系统、云计算平台或系统、大数据平台或系统、物联网、工业控制系统及采用移动互联技术的系统等；先确定边界和受侵害客体，再判定危害程度。
- 通用技术要求覆盖安全物理环境、安全通信网络、安全区域边界、安全计算环境和安全管理中心；管理要求覆盖制度、机构、人员、建设和运维。[cite:7]
- 云计算扩展要求：核验基础设施位置、虚拟化隔离、镜像与快照保护、云环境管理、云服务商选择及云租户间隔离。
- 移动互联扩展要求：管控无线接入点、移动终端、移动应用采购与开发、应用分发和移动接入边界。
- 物联网扩展要求：落实感知节点和网关的物理防护、设备安全、节点管理、数据融合处理及感知网络边界控制。
- 工业控制扩展要求：保护室外控制设备，实施控制网络分区分域、拨号与无线使用控制、控制设备防护，安全变更不得破坏实时性和安全生产。
- 实际对象同时满足相应级别的通用要求与适用扩展要求；大数据等场景结合风险评估采取针对性措施，不得以扩展要求替代通用要求。
- 工作闭环为“定级—备案—安全建设整改—等级测评—监督检查”；第二级及以上对象依法履行备案，边界、业务或危害程度重大变化时重新定级。
- 测评采用 **GB/T 28448-2019《网络安全等级保护测评要求》** 和 **GB/T 28449-2018《网络安全等级保护测评过程指南》**。[cite:8][cite:9]
- 测评过程依次执行测评准备、方案编制、现场测评、报告编制；现场测试前完成授权、风险告知、数据备份和回退准备，结果由双方确认并归还资料。
- 整改闭环为“问题登记—风险定级—责任人与期限—修复或补偿控制—复测取证—批准关闭—基线更新”；延期须有风险接受人、到期日和临时控制，禁止仅凭截图关闭。

#### 1.5 关键信息基础设施保护

- 依据国务院令第 745 号《关键信息基础设施安全保护条例》（2021 年），由保护工作部门制定认定规则、组织认定并通知运营者，不以企业自行声明代替认定。[cite:10]
- 主要负责人对安全保护负总责；设置专门安全管理机构，对机构负责人和关键岗位人员进行背景审查，并保障人员、经费和资源投入。
- 安全保护措施与关键信息基础设施同步规划、同步建设、同步使用，重大网络安全决策应有专门安全管理机构人员参与。
- 每年至少开展一次网络安全检测和风险评估，及时整改并按要求报送；重大事件或重大威胁按规定报告保护工作部门和公安机关。
- 优先采购安全可信产品和服务，签订并监督安全保密协议；采购可能影响国家安全的产品和服务时依法通过网络安全审查。
- 合并、分立、解散或重大变更时及时报告并按要求安全处置设施、账号、密钥和数据，确保责任与控制权连续。

#### 1.6 商用密码与密评

- 依据《密码法》、国务院令第 760 号《商用密码管理条例》（2023 年修订）及《商用密码应用安全性评估管理办法》（2023 年），先判定系统是否属于依法应使用商用密码保护的重要网络与信息系统。[cite:11]
- 基本技术要求采用 **GB/T 39786-2021《信息安全技术 信息系统密码应用基本要求》**，覆盖物理和环境、网络和通信、设备和计算、应用和数据四个技术层面，以及制度、人员、建设运行和应急处置。[cite:12]
- 测评采用 **GB/T 43206-2023《信息安全技术 信息系统密码应用测评要求》**；配套过程和行业要求参照现行 **GM/T 0115-2021**、**GM/T 0116-2021**，并核对最新替代关系。[cite:13][cite:14]
- 规划阶段编制商用密码应用方案并评估，未通过不得作为建设依据；运行前密评未通过的系统须改造且改造期间不得投入运行。
- 建成运行后每年至少开展一次密评；评估报告形成后 30 日内按规定备案，未通过须整改并采取运行期临时保护措施。
- 采用经批准的商用密码算法、协议、产品和服务，验证依法需要的检测认证；重点评价合规性、正确性和有效性，禁止以“使用了国密算法”替代整体密评。
- 密钥生成、分发、存储、使用、轮换、归档、销毁全程受控；私钥和主密钥不得硬编码、明文导出或与密文同库存放，密码事件依法报告并启动应急处置。

### 2. 安全体系建设

#### 2.1 安全域、纵深防御与零信任

- 按业务敏感度、信任级别和故障影响划分互联网接入区、应用区、数据区、管理区、开发测试区及第三方接入区；跨域仅开放经审批的协议、端口和方向。
- 生产与非生产隔离，管理面与业务面隔离，高价值数据域实施微分段；东西向访问默认拒绝并保留流量、身份和策略审计。
- 纵深防御同时覆盖身份、终端、网络、应用、数据、物理和人员流程，任一单点控制失效不得直接导致核心资产完全暴露。
- 零信任遵循 **NIST SP 800-207（2020）**：不因内网位置或设备归属授予隐式信任，访问前分别验证主体与设备，按会话动态授权。[cite:15]
- 策略决策综合用户、服务身份、设备健康、资源敏感度、时间和行为风险；高风险变化触发重新认证、降权或终止会话。
- 策略执行点尽量靠近资源，访问采用短时凭证和最小权限；持续采集策略决策、设备姿态和资源访问日志，不以零信任网关替代应用鉴权。

#### 2.2 最小权限与 IAM/MFA

- 建立统一身份源和账号全生命周期，入职、调岗、离职及外包到期自动触发授权、复核和回收；禁止共享账号，服务账号必须可归属。
- 默认拒绝，按角色或属性授权到资源、动作和数据范围；租户隔离、对象级权限和字段级敏感数据权限在服务端强制执行。
- 管理员、远程访问、云服务控制面和高风险操作启用抗钓鱼能力优先的 MFA；短信仅作为风险权衡后的补充因素，恢复流程不得绕过 MFA。
- 特权账号使用独立凭据、堡垒机或即时提权，实行双人审批、限时授权和会话审计；定期清理长期权限、孤儿账号和未使用访问密钥。
- 权限复核至少由资源所有者确认，敏感角色提高频率；认证日志、授权变更和特权操作统一关联用户、设备、来源、目标及结果。
- 会话令牌具备短有效期、受众和签发方校验，敏感操作重新认证；登出、禁用、改密和风险处置时撤销活动会话及刷新令牌。

#### 2.3 密钥与证书管理

- 建立密钥和证书资产清单，记录所有者、用途、算法、保护级别、签发方、有效期、依赖系统和轮换方式。
- 使用合规随机数源和密钥管理服务或硬件安全模块保护高价值密钥；禁止写入代码、镜像、流水线日志、工单或即时通信。
- 数据加密密钥采用信封加密，与密钥加密密钥分离；按密码模块边界授权，密钥导出、恢复和销毁保留双人控制与审计。
- 证书申请验证域名或主体控制权，私钥不落普通配置库；自动监测到期并轮换，轮换后撤销旧凭据并验证依赖方。
- 疑似泄露立即吊销证书或轮换密钥、撤销会话、调查使用记录并评估历史数据影响；不得只删除公开仓库中的泄密副本。
- 定期测试密钥备份恢复和吊销链，归档密钥仅在合规保留期内可用，到期安全销毁并保留证明。

#### 2.4 日志与审计

- 采集身份认证、权限变更、应用异常、数据库访问、API、主机、网络、安全设备、云平台、容器和密钥操作日志。
- 日志统一时间源和字段规范，包含主体、来源、对象、动作、结果、时间及关联追踪号；跨系统时间偏差须监测和校正。
- 网络日志依法留存不少于六个月；其他日志按等级保护、行业监管、调查和举证需求确定更长期限，形成可审计的保留矩阵。[cite:1]
- 日志传输加密，集中存储并限制删除和修改权限，采用追加写、完整性校验或不可变存储；审计员与系统管理员职责分离。
- 对口令、令牌、密钥、完整证件号和非必要个人信息先脱敏再入日志；建立日志访问审批、容量告警、定期检索和完整性验证。

#### 2.5 备份与容灾

- 依据 **GB/T 20988-2025《网络安全技术 信息系统灾难恢复规范》**（2026 年 1 月 1 日实施）开展业务影响分析，确定 RPO、RTO 和六级灾难恢复能力目标。[cite:16]
- RPO 表示恢复点目标，RTO 表示从事件发生到恢复产品、服务、活动或资源的时间目标；二者均须由业务所有者批准并通过演练验证。
- 下表为组织默认服务分级，不是国家标准统一阈值；业务影响分析可收紧目标，放宽须履行风险审批。

| 服务级别 | 默认 RPO | 默认 RTO | 最低控制 |
| --- | --- | --- | --- |
| 核心连续服务 | 接近 0 | ≤30 分钟 | 同步或近同步复制、自动或半自动切换、独立故障域。 |
| 重要服务 | ≤15 分钟 | ≤4 小时 | 高频复制、备用完整环境、定期切换。 |
| 一般服务 | ≤24 小时 | ≤48 小时 | 每日备份、可用恢复环境、人工恢复。 |
| 可延迟服务 | 按业务批准 | 按业务批准 | 定期备份、配置与数据可重建。 |

- 至少执行“3 份数据、2 种介质、1 份异地”的备份策略，并保留离线或不可变副本；备份账号与生产管理员隔离。
- 备份覆盖数据、配置、密钥恢复材料、镜像和基础设施代码；备份加密并控制跨域复制，过期备份按保留策略安全删除。
- 通过抽样恢复、全流程切换和回切演练验证实际 RPO/RTO；记录依赖、耗时、数据差异和失败项，整改后复测。

### 3. 攻防技术基线（防御导向）

#### 3.1 OWASP Top 10：2021 与 2025 对照控制

- 采用 **OWASP Top 10:2025** 作为当前风险分类，同时保留与 2021 版的映射；Top 10 是风险意识文档，不替代完整安全需求、代码审查和渗透测试。[cite:17][cite:18]
- **A01:2025 访问控制失效**（含 2021 A01 及 SSRF 风险）：成因是服务端未校验对象、功能、租户或目标资源权限；修复为默认拒绝、逐请求服务端鉴权、集中授权策略、SSRF 出口限制及越权自动化测试。
- **A02:2025 安全配置错误**（2021 A05）：成因是默认口令、调试功能、过宽权限和云配置漂移；修复为加固镜像、最小服务、关闭示例与目录列表、配置即代码、持续基线核查。
- **A03:2025 软件供应链失效**（覆盖 2021 A06 并关联 A08）：成因是组件漏洞、依赖混淆、受污染构建或更新；修复为锁定依赖、私有代理仓、SCA、SBOM、签名验证、构建隔离和及时升级。
- **A04:2025 密码学失效**（2021 A02）：成因是敏感数据明文、弱算法、固定密钥或错误随机数；修复为数据最小化、标准算法与 AEAD、正确证书校验、KMS/HSM 和密钥轮换。
- **A05:2025 注入**（2021 A03）：成因是将不可信数据拼接为 SQL、命令、LDAP、模板或表达式；修复为参数化接口、安全 API、上下文校验、白名单和解释器最小权限。
- **A06:2025 不安全设计**（2021 A04）：成因是缺少滥用场景、信任边界和安全业务规则；修复为威胁建模、滥用用例、速率与资源限制、安全设计评审及架构验收门禁。
- **A07:2025 身份认证失效**（2021 A07）：成因是弱口令、可猜测重置流程、会话固定和暴力破解；修复为 MFA、统一认证、抗枚举、限速、安全 Cookie、会话轮换和撤销。
- **A08:2025 软件或数据完整性失效**（2021 A08）：成因是未验签更新、不可信反序列化和不受控 CI/CD；修复为签名校验、可信源、构建证明、制品准入和仅反序列化受限数据格式。
- **A09:2025 安全日志与告警失效**（2021 A09）：成因是缺乏关键事件、日志不完整或无人处置；修复为统一审计、防篡改、可关联告警、值班分派、响应时限和检测规则演练。
- **A10:2025 异常条件处理不当**（2025 新增）：成因是异常泄露、失败开放、资源未释放或状态不一致；修复为统一异常边界、失败关闭、事务回滚、超时与重试上限、通用错误响应和安全降级。

#### 3.2 重点漏洞通用防御规则

- **注入**：所有外部输入视为不可信；SQL 使用预编译和绑定变量，操作系统调用使用无 Shell 的参数数组，LDAP/模板使用专用安全 API；白名单校验只作为补充，数据库账号按最小权限配置。
- **XSS**：按 HTML、属性、JavaScript、URL、CSS 上下文分别编码，优先安全 DOM API；富文本采用成熟白名单净化，禁止拼接动态脚本；CSP 和 `HttpOnly` 仅作纵深防御。
- **CSRF**：对 Cookie 鉴权的状态变更请求校验高熵、会话绑定且一次性的 CSRF Token，并核验 `Origin`；Cookie 设置适当 `SameSite`，跨站关键操作重新认证，禁止把 Token 放入 URL。
- **SSRF**：仅允许业务必要的协议、主机和端口白名单；规范化 URL 后解析 DNS，拒绝环回、私网、链路本地、组播、保留地址及云元数据地址，IPv4/IPv6 均须检查。
- SSRF 每次重定向重新校验目标并限制次数，防 DNS 重绑定应在连接时校验实际地址；通过专用出口代理限制内网访问，禁止只用字符串黑名单。
- **反序列化**：不直接反序列化不可信原生对象，改用 JSON 等简单格式并执行 Schema、长度、深度和类型白名单；完整性与签名只验证来源，不能替代安全解析。
- **越权**：每次请求在服务端同时校验主体、动作、资源所有者和租户；列表、导出、修改、删除采用同一授权策略，随机 ID 或前端隐藏按钮不得视为权限控制。
- **文件上传**：限制数量、大小、扩展名和真实文件特征，MIME 仅作辅助；随机命名、存储到 Web 根目录外、禁止执行，图片重编码，恶意内容扫描后以下载附件方式提供。
- **弱口令**：支持长口令和泄露口令拦截，登录及找回流程限速、风控和告警；口令使用独立盐的 Argon2id 等自适应散列，禁止 MD5、SHA-1 或无盐散列，参数按 OWASP 当前建议校准。[cite:19]

#### 3.3 安全编码检查项

- 在信任边界统一校验来源、类型、长度、范围、编码和业务状态，拒绝非法输入而非仅清洗危险字符。
- 所有输出按接收端上下文编码，日志另作换行和控制字符处理，防止日志伪造。
- 数据访问层统一参数化和租户条件，禁止通过字符串拼接生成查询、命令、路径和表达式。
- 文件路径规范化后验证仍位于允许目录，禁止用户控制绝对路径、设备名或服务端任意协议。
- 业务操作验证当前状态和前置条件，防止重复提交、重放、竞态和跨步骤调用；高风险请求使用幂等键和事务。
- 外部调用设置连接与读取超时、响应大小、重试上限、熔断和隔离舱，避免资源耗尽及重试风暴。
- 错误信息不返回堆栈、SQL、路径、密钥和内部主机信息；异常时关闭失败、释放资源并维持事务一致性。
- 密钥通过受控 Secret 服务注入，代码、配置、镜像、测试样例和日志均不得包含真实凭据。
- 新增依赖经过许可证、来源、漏洞和维护状态检查；构建产物可复现并生成 SBOM，禁止从未知地址动态拉取执行代码。
- 安全单元测试覆盖越权、注入、XSS、CSRF、SSRF、上传、异常和边界值；严重安全回归必须阻断发布。

### 4. CTF 与渗透测试方法的防御转化

#### 4.1 攻击阶段对应的检测与阻断点

- **信息收集**：监测目录与接口枚举、异常 User-Agent、低频分布式扫描、DNS 查询和云资源列举；减少 banner、错误和公开元数据泄露，WAF、API 网关与云控制面联动限速和封禁。
- **初始访问与漏洞利用链**：关联 Web、主机、身份和网络告警，识别单点告警无法呈现的连续行为；在入口过滤、虚拟补丁、EDR 阻断、应用隔离和最小权限处设置多重断点。
- **权限提升**：监测新特权授予、sudo/服务配置变化、令牌滥用、驱动与计划任务异常；及时修补、移除多余权限、限制危险能力并对特权变更双人审批。
- **凭据访问**：检测异常口令尝试、凭据文件读取、目录复制和令牌导出；凭据不落地、限制调试与内存读取、使用短期令牌和分层管理员账号。
- **横向移动**：监测异常 SMB/RDP/SSH/WinRM、服务创建、Pass-the-Hash 迹象和跨租户 API；实施主机防火墙、微分段、管理专用通道、来源约束和横向访问默认拒绝。
- **持久化与渗出**：检测新自启动项、异常计划任务、未知签名制品、长期低频连接及压缩加密后外传；使用应用白名单、出口代理、DLP、流量基线和不可变日志阻断。

#### 4.2 CTF 题型对应的防护原理

- **Web**：将注入、越权、上传、模板和反序列化题转化为统一输入校验、服务端授权、安全解析和回归测试，不以解题 Payload 作为生产测试数据。
- **Pwn**：将内存破坏与利用缓解知识转化为内存安全语言优先、编译保护、ASLR/DEP、栈保护、沙箱、系统调用限制、模糊测试和崩溃归因。
- **Reverse**：将逆向分析转化为恶意样本静态/动态分析、制品签名与完整性验证；客户端不得保存真正秘密，混淆和反调试不得替代服务端控制。
- **Crypto**：将密码题转化为标准算法库、唯一随机数与 nonce、认证加密、协议降级防护和侧信道意识；禁止自研通用密码算法或错误复用密钥流。
- **Misc**：将编码、隐写、取证和流量题转化为文件鉴别、日志时间线、内存与磁盘取证、异常流量分析；未知文件在隔离沙箱处理并记录证据哈希。

#### 4.3 红蓝对抗与 ATT&CK

- 测试必须有书面授权、资产边界、时间窗、允许技术、速率限制、数据处理规则、停止条件、应急联系人和清理要求；禁止未授权生产破坏。
- 红队按威胁场景验证攻击路径，蓝队记录可见性、阻断点和响应动作，紫队共同把发现转化为代码、配置、检测规则和流程整改。
- 使用 **MITRE ATT&CK** 的战术、技术、子技术和数据源建立共同语言；将每项技术映射到资产、日志来源、检测逻辑、预防控制和责任人。[cite:20]
- 先覆盖与行业和资产相关的技术，不以矩阵“全部涂绿”为目标；记录版本、检测置信度、盲区、误报和补偿控制。
- 通过原子化、安全可控的对抗验证规则是否触发、告警是否分派、处置是否完成；以检测覆盖率、平均检测时间、平均遏制时间和复发率验收闭环。

### 5. 安全运营

#### 5.1 漏洞管理流程

- **发现**：统一接收资产扫描、SCA、云配置、基线、渗透测试、供应商通告和外部报送，资产负责人及组件归属必须可定位。
- **去重与验证**：合并同根因问题，确认版本、配置、可达性和实际影响；测试取得授权并保护证据，不因扫描器结果直接判定真实风险。
- **评级**：采用 **CVSS v4.0（2023）** 等表达技术严重性，并结合威胁情报、互联网暴露、资产价值、数据敏感度和现有控制形成修复优先级。[cite:21]
- **修复**：优先官方补丁或升级，不能立即修复时实施访问收敛、虚拟补丁、功能禁用等临时控制；变更须测试、审批并具备回退。
- **复测**：使用同条件和业务回归验证根因消除，检查同类资产与绕过路径；保留版本、证据、复测人和关闭时间。
- **例外**：风险接受须有业务与安全责任人、理由、补偿控制和到期日；到期自动重新评估，禁止永久豁免。
- **度量**：跟踪逾期率、平均修复时间、复发率、资产覆盖率和未知组件率，按根因改进开发、采购和配置流程。

#### 5.2 应急响应 PDCERF

- **准备（Preparation）**：维护联系人、资产与依赖、预案、取证工具、备份、替代通信和演练；预先明确监管、法务、公关和管理层升级路径。
- **检测（Detection）**：确认事件范围、时间线、入口、受影响账号与数据，保存原始日志和易失证据，记录采集人、时间、来源与哈希。
- **遏制（Containment）**：优先隔离主机、禁用账号、撤销令牌、阻断域名或分段网络；保留必要证据并评估业务中断和攻击者反制风险。
- **根除（Eradication）**：清除恶意制品和持久化，修复入口、轮换相关凭据、修补同类资产；仅重装主机而未消除根因不得关闭事件。
- **恢复（Recovery）**：从可信备份和干净制品分阶段恢复，验证完整性、安全基线和业务功能，持续加强监测并准备回退。
- **跟踪（Follow-up）**：完成复盘、根因和影响评估，更新规则、预案、培训及风险台账；行动项指定责任人和期限并复测。
- 按 2025 年《国家网络安全事件报告管理办法》履行报告：较大以上事件涉及关键信息基础设施的，最迟 1 小时报保护工作部门和公安机关；中央和国家机关相关部门最迟 2 小时报本部门网信工作机构；其他网络运营者最迟 4 小时报属地省级网信部门，均须同时遵守“第一时间”及行业更严要求。[cite:25]
- 初报信息不全时先报已知情况并持续补报，不得等待完整归因而延误；适用该办法的事件处置结束后 30 日内按原渠道报送总结，对外通知和证据披露由授权角色统一执行。

#### 5.3 威胁情报、SIEM 与 SOAR

- 情报记录来源、时间、置信度、适用行业、有效期和共享限制；优先消费与资产相关的 TTP、漏洞利用和基础设施信息，过期 IOC 自动降级或退出。
- 情报映射到 ATT&CK、资产和检测规则，进入阻断列表前评估误报与共享基础设施风险；共享前脱敏并遵守法律和情报共享协议。
- SIEM 统一采集、解析、时间同步和实体标识，规则采用阈值、序列、统计基线和威胁情报关联，覆盖身份、终端、网络、云、应用和数据。
- 每条规则记录用途、ATT&CK 映射、数据依赖、查询逻辑、严重度、误报处理、负责人和版本；通过历史回放与对抗测试验证，不以“已启用”代表有效。
- 高价值关联包括异地或异常认证后敏感访问、漏洞扫描后利用成功、权限提升后横向连接、批量读取后异常外传；告警须带调查上下文。
- SOAR 剧本（playbook）明确触发条件、证据丰富、审批、执行、回滚和审计；封禁核心网络、停用大量账号、删除数据等操作必须人工批准。
- 建立告警去重、抑制和升级规则，监测数据源中断与规则失效；处置动作使用最小权限独立账号并防止自动化死循环。

#### 5.4 基线核查与云原生安全

- 按产品和实际版本选择 **CIS Benchmarks**，形成“自动扫描—人工确认—整改—复测—例外审批”闭环，禁止把其他版本条目机械套用。[cite:22]
- 主机、数据库、中间件、网络设备和云账号建立加固模板；检测默认账号、服务端口、补丁、权限、审计、密码套件和配置漂移。
- 参考 **NSA/CISA Kubernetes Hardening Guidance v1.2（2022）**，并匹配对应版本的 CIS Kubernetes 或托管 Kubernetes Benchmark。[cite:23]
- Kubernetes API 启用强认证、最小权限 RBAC、审计和入口限制；etcd 加密并限制访问，Secret 使用受控外部密钥服务，禁止 service account 令牌无必要自动挂载。
- Pod 默认非 root、只读根文件系统、禁止特权容器和宿主机敏感挂载，移除多余 capabilities，设置 seccomp，并按平台使用 SELinux 或 AppArmor。
- 使用 NetworkPolicy 限制 Pod 与命名空间东西向流量，配置资源请求、限制和配额；控制面、节点和工作负载及时升级，禁止使用停止支持版本。
- 镜像来自批准仓库，固定不可变摘要，构建时及入仓后执行漏洞、恶意软件和 Secret 扫描；生成 SBOM、签名并在准入时验证。
- 高危漏洞或未签名镜像阻断部署，例外限时并隔离；运行时检测异常进程、提权、反向连接、敏感挂载和容器逃逸迹象，支持隔离节点或终止工作负载。
- CI/CD 分离构建与部署权限，保护流水线定义和制品库；生产变更经签名制品准入和审批，禁止运行时手工修改形成不可审计漂移。

### 6. 数据安全

#### 6.1 分类分级与全生命周期控制

- 采用 **GB/T 43697-2024《数据安全技术 数据分类分级规则》**，按业务属性和影响对象分类，将数据识别为核心数据、重要数据或一般数据，并叠加个人信息、敏感个人信息等管理标签。[cite:24]
- 建立数据目录，记录所有者、来源、目的、字段、位置、流向、共享方、系统边界、保留期限和级别；级别变化触发权限、加密、审计和出境策略更新。
- 采集前验证必要性和来源合法性，传输与使用按级别授权，共享前评估接收方，归档实施只读和完整性保护，到期删除或匿名化并验证副本。
- 测试、分析和模型训练优先使用匿名化或合成数据；确需生产数据时单独审批、最小抽取、隔离环境、禁止外发并在到期后清理。
- 数据导出、批量查询、公开 API 和跨域复制设置额度、审批、水印或追踪标识；重要数据操作加强实时审计和异常行为阻断。

#### 6.2 脱敏与匿名化算法

- **掩码**：仅展示必要片段，如保留证件首尾少量字符；规则按角色和场景配置，前端遮罩不能替代服务端返回字段裁剪。
- **替换或令牌化**：用无意义令牌替换标识符，映射表独立加密、严格授权并审计；可逆令牌化属于去标识化，不等于匿名化。
- **泛化与抑制**：将精确日期转为区间、精确地址转为较大区域，或删除高识别字段；泛化程度以重识别风险和业务可用性共同确定。
- **扰动与随机化**：对数值或统计结果加入受控噪声，防止单条记录反推；统计发布采用差分隐私时须管理隐私预算和组合查询风险。
- **k-匿名**：发布前确保每条记录在准标识符组合上至少与 `k-1` 条其他记录不可区分；准标识符须结合外部可关联数据识别。
- k-匿名不能单独防御同质性和背景知识攻击；敏感属性场景结合 **l-多样性** 或 **t-接近性**，并评估分组、排序和多次发布造成的组合重识别。
- 匿名化须达到无法识别特定自然人且不能复原的程度；去标识化、假名化、掩码和加密后的信息仍可能是个人信息，应持续受控。[cite:3]
- 建立重识别风险评估和攻击测试，记录数据集版本、算法参数、外部数据假设和残余风险；用途、关联数据或发布对象变化时重新评估。

#### 6.3 加密选型与 DLP

- 传输默认使用 TLS 1.2 及以上并优先 TLS 1.3，禁用明文协议及过时 SSL/TLS 版本；校验证书链、主机名和有效期，高价值服务间通信采用双向认证。
- 有商用密码合规要求时采用批准的算法、协议、产品和服务，完成相应密评；不得用自定义“国密兼容”实现替代合规验证。
- 存储按字段、文件、数据库或磁盘分层加密，敏感字段优先应用层或字段级保护；磁盘加密不能替代应用授权和导出控制。
- 新业务优先认证加密模式，确保机密性、完整性和真实性；nonce/IV、随机数和标签处理遵循算法库规范，禁止 ECB、固定密钥和自研协议。
- 采用 KMS/HSM 和信封加密，数据密钥与主密钥分离并定期轮换；备份、快照、日志、缓存、搜索索引和消息队列执行同等级保护。
- DLP 先完成数据发现与标签，再覆盖终端、邮件、Web、云盘、API 和可移动介质；结合精确数据匹配、指纹、关键字、OCR 与行为上下文降低误报。
- 策略按级别执行告警、审批、加密、隔离或阻断，批量下载与非工作时段外传提高风险分；例外须最小范围、限定期限并保留审计。
- DLP 事件只保留调查所需最少样本，敏感原文隔离保存；定期复核误报、漏报、绕行渠道和策略有效性，不得把监控用于无关目的。

## 第四篇 IT 产品界面设计规范

### 一、设计总则与适用边界

本规范适用于桌面 Web、移动 H5、iOS、Android、B 端后台、电商页面与数据可视化界面。
界面设计的目标不是装饰屏幕，而是让用户以可预期、可恢复、可负担的成本完成任务。
设计决策依次服从：安全与合规、任务成功、无障碍、效率、一致性、品牌与美感。
业务目标与用户目标冲突时，不得通过隐瞒、误导或增加退出成本换取短期转化。
以“战略—范围—结构—框架—表现”组织设计：先明确目标，再定义功能、流程、布局与视觉。
任何视觉稿都必须能追溯到用户任务、业务规则、内容来源和异常状态。
经典原理用于形成假设，不能代替目标用户研究、可用性测试和真实数据分析。
平台规范是底线而非模板；跨端保持任务与语义一致，不强求控件外观完全相同。
尺寸单位必须区分：Web 使用 CSS px，iOS 使用 pt，Android 使用 dp/sp，不直接等同于物理像素。
不以具体手机型号或固定分辨率定义设计，按可用窗口、输入方式、字号设置和内容压力适配。
本文中的数值分为“标准底线”和“项目基线”；更严格的项目要求可覆盖项目基线，不得降低法规与平台底线。
每次版本发布必须同时检查正常流程、边界数据、异常流程、无障碍和性能降级体验。

#### 设计交付的基本原则

- 先内容后装饰：没有真实或合理近似内容，不进入高保真设计。
- 先流程后单页：先画任务流、状态流和返回路径，再绘制关键页面。
- 先预防后报错：能约束非法输入，就不要等用户提交后责备用户。
- 可逆优先：删除、覆盖、支付、授权等操作优先考虑撤销、草稿、版本恢复或二次确认。
- 识别优于回忆：展示可选对象、历史记录和上下文，减少用户记忆命令与编码。
- 一致而非僵化：同类任务一致，不同风险、频率、输入方式应有可解释的差异。
- 渐进披露：优先呈现当前决策所需信息，高级能力可发现但不挤占主路径。
- 反馈闭环：每次输入都应获得即时或可追踪的系统状态反馈。

### 二、界面设计底层逻辑

#### 用户目标与心智模型

用户心智模型是其基于经验形成的“系统如何工作”的解释，产品概念模型是界面实际呈现的规则。
设计者模型、代码实现模型与用户心智模型不一致时，表现为找不到、看不懂、怕点错和反复学习。
通过访谈、现场观察、客服记录、搜索日志和任务分析提炼目标，不直接把用户提出的方案当需求。
按“角色—情境—目标—现有做法—障碍—成功标准”记录核心任务，区分用户目标与操作步骤。
用任务动词命名页面和动作，例如“创建报销单”，避免用数据库术语或组织内部黑话。
优先沿用用户已掌握的平台惯例，如返回、关闭、收藏、购物车；创新必须带来可测收益并提供学习线索。
概念隐喻只借用帮助理解的规则，不复制现实物品的全部外观与限制。
同一对象在全产品中保持名称、属性、状态和动作一致，不能一处称“项目”、另一处称“应用”。
对新手提供示例、空态引导和安全的首次成功；对专家提供批量、快捷键、默认值与自定义。
需要改变既有心智模型时，先用可交互演示和小步反馈建立预期，不能只靠一篇帮助文档。
每个核心页面写清一句设计命题：“谁在何种情境下，完成什么，下一步去哪里”。
验收时观察用户能否预测操作结果，而非仅询问其是否“喜欢”界面。

#### 信息架构

先建立内容清单与对象模型，明确对象、属性、关系、所有者、生命周期和权限，再决定菜单。
开放式卡片分类用于探索用户如何分组与命名；封闭式卡片分类用于验证候选结构。
卡片分类结果受样本和题目影响，需结合树测试验证“能否找到”，结合任务测试验证“能否使用”。
分类优先按用户任务与稳定对象组织，不照搬公司部门、数据库表或研发服务边界。
同一层级尽量采用互斥且共同穷尽的分区；交叉属性使用筛选、标签或关联，不复制出多份真相。
层级追求浅而平衡，但不机械执行“三次点击定律”；每次选择明确比减少一次点击更重要。
核心任务建议不超过三次有意义的导航决策，常用对象应可从收藏、最近使用或全局搜索直达。
顶层导航数量以可扫描为准，通常从四至七项候选起步并测试，不以“7±2”作为硬上限。
全局导航回答“产品有什么”，局部导航回答“这里有什么”，上下文导航回答“与当前对象相关还有什么”。
面包屑表达真实层级并提供上级入口，不能替代全局导航；首页通常不作为可点击的当前节点。
搜索适合明确目标与海量内容，导航适合探索与理解范围，两者应共享同义词和对象命名。
移动底部主导航保留三至五个高频平级目的地；低频功能进入页面内导航或“更多”，不可频繁变动位置。
当前位置、选中态、返回去向和未读状态必须明确，浏览器返回与系统返回不得意外丢失上下文。
导航标签使用用户语言，避免只有图标的陌生主导航；图标与文字并存时含义不得相互矛盾。
信息架构评审至少覆盖首访、回访、深链进入、无权限、跨角色和跨语言场景。

#### 交互成本：菲茨、希克与记忆规律

菲茨定律指出，指向时间与目标距离、有效尺寸相关，常用形式为 `T = a + b × log2(1 + D / W)`。
提高可达性的直接手段是缩短移动距离、扩大有效热区、稳定目标位置，而非仅放大可见图标。
高频主操作靠近当前上下文和指针自然停留区；低频危险操作远离主操作，避免肌肉记忆误触。
桌面屏幕边缘和角落对鼠标具有“无限边缘”优势，但该优势不能直接套用到触屏拇指操作。
相邻主操作与危险操作保留足够间隔，弹窗按钮顺序遵循平台惯例，不在不同页面任意交换。
希克定律说明选择时间会随可选信息量增加，常见近似写为 `T = a + b × log2(n + 1)`。
减少选择成本的顺序是删除无关项、提供合理默认、按任务分组、突出推荐项，最后才是隐藏高级项。
不对所有选项机械排序；高频、风险、相关性和用户最近选择都可能比字母顺序更有效。
搜索建议、自动完成和最近使用可把“自由回忆”转化为“识别选择”，但必须允许忽略建议继续输入。
米勒“7±2”描述特定实验条件下的短时记忆容量，不是菜单、标签页或轮播图的通用数量规范。
现代研究更常以约四个组块作为注意条件下工作记忆的保守参考，实际容量受材料与经验影响。
组块化依赖用户已有知识；专家眼中的一个组块，可能是新手的多个陌生概念。
不把复杂任务拆成许多需要记住前文的页面；跨步骤信息应可见、可回看、可自动带入。
用真实任务测量完成时间、错误率和回溯次数，不能只用点击数评价交互成本。

#### 格式塔原理与界面分组

接近：相关元素距离小于组间距离；标签靠近所属控件，组间距显著大于组内间距。
相似：同功能控件共享形状、字重或色彩，但相似不能替代语义，也不能只用颜色区分状态。
连续：对齐边缘、轴线和阅读方向，使视线沿连续路径移动；表格数字与表头必须形成稳定列线。
闭合：用户会补全不完整轮廓，可用于简洁图标和进度表达，但不得损害识别与屏幕阅读器语义。
共同区域：卡片、背景或边界可形成强分组；分组已能靠留白表达时，不再叠加边框与阴影。
图形与背景：前景必须能从背景中浮现，图片上的文字需有稳定遮罩或实色承载并实测对比度。
相似原则用于建立组件语法，接近与共同区域用于建立对象关系，连续用于建立浏览路径。
避免“每个区块都卡片化”：过多容器会增加视觉噪声、割裂连续信息并压缩有效内容。
分组后同时进行眯眼测试和语义检查，确保视觉关系与代码中的标题、列表、表格关系一致。

#### 视觉层级与视线流

视觉层级由位置、尺寸、字重、明度差、色彩、留白和运动共同构成，不只靠放大标题。
每个视图确定一个首要信息和一个主动作；多个同权重按钮会迫使用户重新比较。
F 型扫描常见于从左到右阅读的密集文本页，重要标题、关键词和结论应靠前呈现。
Z 型视线适合内容稀疏、目标单一的展示页，可串联品牌、价值、证据和主动作。
F/Z 是观察结果而非强制模板，不适用于所有语言、任务、移动端和熟练用户的任意浏览行为。
从右到左语言应镜像阅读顺序；移动窄屏通常转为纵向扫描，不能照搬桌面 Z 型构图。
长文使用有意义的标题、摘要、列表和段首关键词支持扫读，避免整页居中或连续加粗。
动效会抢占注意，只用于解释状态、空间关系或反馈；核心任务旁不设置自动轮播与闪烁。
用五秒测试验证首要信息，用眼动或行为数据验证复杂页面，不以设计者的视线替代用户证据。

#### 认知负荷控制

内在负荷来自任务本身，外在负荷来自不恰当呈现；设计应减少后者，并通过分步与示例管理前者。
一屏只要求用户处理当前决策所需的信息，不把所有说明、术语和高级设置同时展开。
保持相关控件与反馈在空间和时间上邻近，避免用户在字段、帮助文档和结果之间反复对照。
删除重复导航、无意义装饰、冗余文案和不影响决策的实时变化，提升信噪比。
复杂流程提供总览、当前位置、预计步骤和可回看的摘要，避免不可预测的动态增长。
默认值、自动带入和历史记录可减少输入，但涉及费用、权限、公开范围和隐私时必须再次明确。
新手帮助应在情境中出现并可跳过；专家可关闭提示，不让教学层长期阻塞任务。
使用任务成功率、耗时、错误、求助次数和主观难度共同评估负荷，不能只看页面元素数量。

### 三、人体工程学与无障碍

#### 触控目标与拇指热区

iOS/iPadOS 常规控件采用不小于 `44×44 pt` 的项目基线，Android 采用不小于 `48×48 dp`。
Web 的 WCAG 2.2 AA 目标尺寸最低标准为 `24×24 CSS px` 及规定例外；产品对粗指针仍采用更舒适的 `44×44 CSS px`。
可点击热区可以大于可见图标，但热区不得与相邻操作重叠，也不能通过透明 padding 掩盖误触风险。
高频图标按钮之间建议至少保留 `8 dp/pt` 的视觉间隔，危险操作另加距离或隔离区域。
列表整行可点击时，行内次要按钮必须有独立热区与事件边界，不得出现点击歧义。
不要只放大图形而不扩大热区，也不要把极小文字链接作为触屏上的唯一关键入口。
拇指热区随设备尺寸、握持方式、左右手与姿态变化，应通过真机测试而非固定“绿色区域图”判断。
高频操作优先落在自然握持可达的下半屏；顶部适合标题、状态和低频返回，超大屏不得机械铺满。
底部主动作需避开系统手势区、安全区和浏览器工具栏，软键盘弹出时仍可到达。
左右手都能完成核心任务，滑动、长按、多指等手势必须提供可见按钮等价路径。

#### 视距、字号与视觉疲劳

字号应从视角、阅读距离、字体实际字形和用户缩放设置推导，不能用“屏幕越大字号越大”简单换算。
Web 正文项目基线为 `16 CSS px`，中文长文通常采用 `16–18 CSS px`；移动端遵循系统动态字号。
iOS 正文通常从系统 Body 的 `17 pt` 起步，Android 正文常以 `16 sp` 起步，并支持系统字体缩放。
辅助文字不能因标为“次要”而不可读；非必要装饰性小字不承担价格、权限、错误等关键信息。
正文允许在不借助辅助技术时放大至 `200%`，放大后不丢失内容与功能。
高对比不等于高刺激；大面积高饱和色、纯亮白背景与快速亮度切换会增加疲劳。
深色环境降低整体亮度并控制蓝光不是唯一答案，应提供主题选择并尊重系统设置。
长文行宽、行高与字重共同影响疲劳；大屏需限制阅读列宽，而不是让一行横跨整个显示器。
大屏、电视和会议投屏按实际最远观看距离单独验证，不沿用桌面正文字号。

#### 对比度与颜色可辨识性

WCAG 2.2 AA 要求普通文字与背景对比度至少 `4.5:1`。
大号文字至少 `3:1`；WCAG 的大号指常规约 `18 pt/24 CSS px` 或粗体约 `14 pt/18.66 CSS px`。
识别控件边界、状态和必要图形对象所需信息，与相邻颜色的对比度至少 `3:1`。
对比度按实际前景、背景及透明度合成后的颜色计算，不能只比较设计变量中的两个十六进制值。
文字置于图片、渐变或视频上时，对最不利位置取样，并使用稳定遮罩保证全帧可读。
禁用组件、纯装饰和标识文字在标准中有例外，但项目仍应保证需要理解的禁用原因可被获取。
错误、成功、警告、等级和图表序列不得仅靠红绿或色相区别，需加文字、形状、图标或线型。
焦点指示与相邻颜色保持清晰差异，不能被 `outline: none` 移除而没有等价替代。
浅色、深色、高对比主题分别自动检测并人工复核，不能以“反色后看起来清楚”作为验收。

#### 键鼠、触屏与其他输入方式

桌面键鼠支持精确悬停、右键、快捷键和多窗口；触屏没有可靠悬停，核心信息不能只在 hover 出现。
所有鼠标可完成的核心任务都应可仅用键盘完成，Tab 顺序与视觉顺序一致且没有键盘陷阱。
焦点进入弹窗后留在弹窗内，关闭后返回触发控件；Esc 行为一致且不会意外丢失未保存内容。
快捷键是效率增强而非唯一入口，不与浏览器、操作系统和输入法常用快捷键冲突。
拖拽排序、缩放和滑块必须提供单击、按钮或数值输入等单指针替代方式。
触屏考虑手指遮挡、滚动与点击冲突、长按系统菜单、横竖屏和软键盘，桌面考虑指针精细定位。
语音、开关控制和屏幕阅读器依赖清晰的控件名称、角色、状态和值，不只依赖坐标操作。
输入方式可在任务中途切换，不因连接键盘、鼠标或辅助设备而重置当前进度。

#### WCAG 2.2 AA 与语义要求

按“可感知、可操作、可理解、健壮”组织无障碍验收，自动扫描与人工测试缺一不可。
优先使用原生 HTML、系统控件与平台语义；自定义组件必须提供正确的名称、角色、状态和值。
页面具备唯一标题、合理标题层级和地标区域；视觉列表、表格、按钮与链接在代码中保持对应语义。
信息图片提供等价替代文本，装饰图片对辅助技术隐藏，图标按钮名称描述动作而非外观。
输入框有持久可见标签，placeholder 只作示例；必填、格式、长度和错误通过程序化关系关联。
焦点始终可见且顺序合理；WCAG 2.2 AA 还要求焦点不得被作者创建的粘性头部、弹层等完全遮挡。
状态消息、异步保存结果和错误摘要应被屏幕阅读器适时播报，避免打断正在输入的用户。
在 `320 CSS px` 宽度的纵向回流条件下，内容不丢失且无需双向滚动；二维数据表等必要内容可例外。
支持文本放大 `200%`，并验证系统大字体、浏览器缩放、翻译变长和文本间距调整后的布局。
表单重复信息可自动带入或选择，除安全等正当原因外，不让用户在同一流程反复输入相同内容。
认证允许粘贴密码、密码管理器和等效替代，不将记忆、转录或拼图等认知测试作为唯一途径。
为音频提供文字稿，为预录视频提供字幕；关键音效、语音反馈和振动同时提供视觉或触觉等价信息。
尊重 `prefers-reduced-motion` 与系统减弱动态效果设置，非必要视差、缩放、翻转和自动运动可关闭。
任何内容每秒闪烁不得超过三次安全阈值；加载动画不用高频闪烁表达繁忙。
无障碍缺陷按任务阻断程度定级，关键流程存在键盘不可达、语义缺失或对比不足时不得上线。

### 四、行为心理学与伦理边界

#### 心理学原理的合规使用

峰终定律：重点设计任务中的关键成功时刻与结束反馈，例如结果确认、凭证、下一步和可追踪入口。
峰终定律不能掩盖流程中的真实困难；错误恢复、等待和取消体验同样进入整体评价。
损失厌恶：在不可逆操作前清楚说明会失去什么，并优先提供撤销，不夸大损失迫使用户同意。
默认效应：默认只选择低风险、可逆、符合多数用户合理预期的选项，并允许便捷修改。
社会证明：展示真实、可核验、与当前决策相关的评价和采用情况，同时标注样本、时间与适用范围。
承诺与一致：让用户自愿完成小步骤、保存进度并确认目标，不利用先前选择强迫其接受后续不合理条款。
目标梯度：用真实已完成步骤和剩余工作量激励继续，不制造虚假进度或永远差一步的奖励。
稀缺效应：仅在库存、席位或截止时间真实且可核验时展示，不循环重置倒计时。
互惠与奖励：可提供无附加条件的试用、模板或帮助，不以小礼物换取隐蔽授权。
自主与控制：提供清晰退出、跳过、撤销和设置权，避免用连续弹窗消耗用户意志。
情绪设计应增强理解与信任，不用可爱插画淡化扣款、数据共享、权限扩大等高风险后果。
行为实验同时观察退款、投诉、取消、长期留存和弱势群体影响，不只优化即时点击率。

#### 暗黑模式负面清单

禁止隐藏费用或在最后一步才出现不可选费用，总价及计费周期应尽早可见。
禁止默认勾选营销订阅、公开个人信息、非必要授权、附加商品或自动续费。
禁止“接受”高亮而“拒绝”隐藏、弱化或需多层寻找，关键选择的接受与拒绝应同样清晰。
禁止双否定、诱导性按钮和 Confirm-shaming，例如用“不，我不需要省钱”羞辱拒绝者。
禁止注册容易取消困难，线上可开启的服务应提供同等便捷的线上关闭或取消路径。
禁止把广告伪装成正文、下载按钮或系统提示，赞助内容必须可识别。
禁止伪造销量、评价、在线人数、库存、倒计时或“刚刚有人购买”等社会证明。
禁止未经明确操作把商品、保险、服务加入购物车或订单。
禁止反复弹窗、无限挽留、伪装关闭按钮，以及点击关闭后仍跳转推广页。
禁止通过视觉弱化、繁琐步骤或不对称措辞阻碍隐私设置、删除账户和数据导出。
禁止用连续授权引导扩大权限，权限请求必须对应用户当下动作并说明用途。
禁止用免费试用掩盖到期扣款；价格、周期、续费日期和取消方式在确认前完整展示。
面向儿童、老人及其他易受影响群体时提高保护标准，不利用其理解或操作障碍获利。
任何增长需求若需要依赖上述模式实现，应退回产品策略评审，而非进入视觉优化。

### 五、美学基础与视觉语言

#### 栅格、间距与布局

栅格用于建立对齐、比例与响应式规则，不是为了把内容切成等宽卡片。
桌面内容型 Web 常用十二列，复杂 B 端可使用二十四列细分；移动可从四列、平板八列起步。
列数、沟槽与页边距随窗口变化，组件跨列由内容和任务决定，禁止为了填满栅格拉伸正文。
采用以 `4` 为基础、`8` 为主节奏的间距体系，常用 `4/8/12/16/24/32/48/64`。
间距优先表达关系：标签与控件、标题与正文的距离应小于组间距离。
同类页面共享内容最大宽度、页边距和操作区位置，避免跳转时布局重心无规律移动。
舒适与紧凑密度可改变行高和留白，但不得缩小最低触控热区或牺牲文字可读性。
对齐以视觉与语义双重校验，图标、文本、数字和输入框需要时进行光学微调。
响应式重排保持信息优先级，不是简单把多列逐列堆叠到移动端。
安全区、浏览器动态工具栏、折叠屏铰链和桌面多窗口都纳入可用布局区域计算。

#### 字体排印

中文优先系统无衬线字体，并设置覆盖 Windows、macOS、iOS、Android 的字体回退链。
每套产品建立一个字阶，可采用约 `1.2–1.25` 的倍率，常用 `12/14/16/20/24/32/40`。
正文常规字重以 `400` 为基线，强调常用 `500/600`，全产品通常不超过三种字重。
不使用伪粗体、伪斜体和过细字重承担正文；小字号更需要足够字重与清晰字形。
界面文字行高通常为字号的 `1.4–1.6` 倍，中文长文可为 `1.5–1.8` 倍，标题可为 `1.2–1.4` 倍。
长文桌面每行约 `28–40` 个汉字作为起始测试值，再按字体、字号、内容密度和人群实测调整。
中西文混排保持基线与标点一致，数字与单位、中文与拉丁词间的间距使用统一排版规则。
正文不随意增加汉字字距；全大写英文短标签可适度增加 tracking，长英文不全部大写。
数字表格采用等宽数字特性，金额、百分比和时间的小数位、千分位及对齐方式一致。
标题避免孤行，中文标点避免出现在不合适的行首；容器变宽变窄时不出现单字悬挂。
正文采用顺应阅读方向的对齐，窄列不强制两端对齐形成大空隙。
品牌字体只用于合适的展示场景，正文、表单和数字优先采用高可读、授权明确的字体。
系统动态字体放大时允许换行、增高和重排，禁止固定高度裁切文字。
文案是界面组件的一部分：按钮使用明确动宾结构，标题可扫描，错误信息给出修复动作。

#### 色彩系统与深色模式

色彩按角色管理，而非按页面随手取色：品牌、表面、内容、边框、交互、成功、警告、错误、信息。
主色用于品牌与关键交互，功能色表达稳定语义，中性色承担绝大多数表面、文字和分隔。
`60-30-10` 可作为主背景、辅助区域与强调色的构图起点，不是必须精确执行的比例或无障碍证明。
强调色面积越小越能突出主动作；整页高饱和主色会削弱层级并增加疲劳。
色相、明度、饱和度共同使用，优先用明度差建立前景与背景的可辨识关系。
每个彩色角色同时定义其承载内容色，例如 `primary` 与 `on-primary`，禁止各自独立选色。
成功、警告、错误和信息色在浅色、深色、高对比主题中分别校验，并保持语义跨端一致。
数据可视化色板与状态色板分开管理，避免图表蓝色被误解为可点击、红色被误解为错误。
深色模式不是简单反相：重新定义表面层级、内容、边框、阴影、图片与图表颜色。
深色主题减少大面积高饱和色，控制主色亮度，使彩色文字和控件在深色表面上仍满足对比度。
暗色界面中的高层级表面可适度提亮以替代浓重阴影，同时保留边框或色调差异。
图片、插画、品牌标志和系统键盘等外部内容逐项目测，必要时提供深色专用资产。
自动强制反色只能作为开发辅助，不能替代设计过的深色主题与逐页走查。

#### 留白、节奏、图标与插画

留白是分组和聚焦工具，不是尚未填满的空白；先通过留白分组，再考虑边框和阴影。
页面节奏由重复的字阶、间距、对齐和组件高度形成，局部变化只用于表达真实层级变化。
对称构图适合稳定与仪式性内容，非对称平衡可引导视线，但都必须保持主动作清晰。
图标采用统一网格、视角、圆角、端点和描边粗细，常见基线为 `24` 网格与约 `1.5–2` 描边。
线性、面性、双色风格不得无规则混用；选中态可以转换风格，但含义与位置保持稳定。
熟悉图标仍需测试，陌生或高风险动作附文字标签，不能要求用户猜测抽象图标。
插画服务于解释、空态或情绪缓冲，不遮挡任务信息，不重复堆砌相同人物与无关装饰。
插画的人物、场景和文化表达保持包容，错误页不将责任归咎用户。
资产使用可缩放的 SVG 或合适的现代位图格式，提供必要替代文本、尺寸和深色版本。

### 六、各应用场景设计规范

#### B 端后台

后台首页围绕角色任务组织待办、异常、常用入口与关键指标，不堆叠所有模块的宣传卡片。
列表页采用“标题与主操作—筛选—表格—分页”的稳定顺序，批量操作与当前选择范围相邻。
文本左对齐、数字右对齐，同列小数位一致；ID、状态、金额和时间采用可复制且可扫描的格式。
表头含义明确，排序方向可见；固定表头或关键列不得遮挡焦点与横向滚动内容。
列宽支持内容压力，关键列可冻结，非关键列可隐藏或调整；截断内容提供不依赖 hover 的查看方式。
筛选优先展示高频条件，高级条件渐进展开；已生效条件以标签呈现，并可单项移除和全部重置。
筛选结果数量、查询时间和空结果原因清晰，筛选与排序状态在返回、刷新或分享链接时按需求保留。
即时筛选避免每次按键造成频繁请求；重型查询使用明确的“查询”动作并防止重复提交。
批量选择必须区分“本页已选”与“全部结果已选”，跨页选择后持续展示对象数量。
批量删除、停用、导出等操作显示影响范围，危险操作确认包含对象名称或数量。
可逆批量操作优先提供撤销；不可逆操作需要适当权限与确认，不能只用通用“确定吗”。
详情页按摘要、核心字段、关联对象、操作记录组织，编辑返回后保留原列表上下文。
表单默认单列，短且强相关字段可同行；标签置顶，必填与选填规则全局统一。
实时校验通常在字段失焦后执行，提交时聚焦并关联错误摘要，不能用弹窗逐条打断。
保存分为草稿、提交和发布等不同语义，离开未保存页面时明确说明后果。
无权限按钮可隐藏或禁用，但必须遵循权限模型并避免泄露受限对象；需要时解释申请路径。

#### C 端移动 App

一级目的地使用三至五个底部标签或平台对应导航，当前位置始终明确。
二级页面保留可靠返回，深链进入时提供回到产品主结构的路径，不制造无法退出的孤岛。
模态只用于必须立即处理的短任务，复杂创建流程使用完整页面并支持保存草稿。
Feed 卡片突出标题、来源、关键媒体与主要动作，减少同权重标签和装饰性数字。
无限滚动提供加载位置反馈与失败重试，页脚、返回顶部和其他目的地仍可到达。
骨架屏匹配真实结构，不伪造内容；下拉刷新不是唯一刷新方式，自动更新不得打断阅读位置。
详情页先回答“是什么、与我何关、现在能做什么”，主操作置于易达区域并避开系统手势区。
个人中心优先账户、订单、隐私、安全、帮助和设置，不用营销入口挤压关键服务。
点赞、收藏等乐观更新失败时回滚并解释，支付、发布等不能假设成功的操作不得提前展示最终成功。
推送、定位、相机、通讯录等权限在具体动作发生时申请，被拒绝后提供系统设置指引和替代路径。
登录过期保存可保留的输入，重新认证后返回原任务，而非一律回首页。

#### 电商转化页

商品页优先呈现名称、规格、真实价格、促销条件、库存、配送、退换与评价，不让用户到结算才发现限制。
主图支持清晰缩放，规格选择与库存联动，不可选组合在操作前可识别。
立即购买、加入购物车、收藏分别服务明确购买、继续比较和稍后决策，不用同一流程强迫所有用户。
评价标注真实购买、时间和规格，允许查看差评与筛选，不伪造热度或只展示片面好评。
优惠规则用可计算的方式说明，优惠券、满减、税费、运费和会员价在结算前形成清晰总价。
支持游客结算或解释注册价值，地址、发票和配送信息可复用且可修改。
提交订单后以防重复提交状态处理支付等待，失败保留订单上下文并明确是否扣款。
成功页给出订单号、支付结果、配送预期、凭证与后续操作，不只显示营销推荐。
转化实验同时监测退单、投诉与退款，不把意外点击或隐藏附加商品计入设计成功。

#### 数据可视化大屏

先区分实时监控、指挥决策与分析探索，再确定刷新频率、信息密度和交互方式。
首屏能在五秒内回答整体状态、主要异常、影响范围与数据更新时间。
每个指标标注定义、单位、统计口径、时间范围和数据来源，实时数据同时展示延迟或离线状态。
趋势用折线、比较用条形、构成谨慎使用堆叠或饼图，关系用散点；不因视觉冲击使用三维图表。
柱状图长度比较通常从零基线开始，截断轴必须具有充分理由并明确标示。
双轴图容易造成虚假相关，优先拆分、归一化或小型 multiples；无法避免时清楚对应轴与单位。
图表色彩数量受控，类别过多时突出关键系列、合并长尾或改用表格，不依赖逐个图例来回记忆。
自动刷新不清空筛选、不重置滚动和缩放，数值剧烈变化提供稳定排序与适当过渡。
大屏远距离文字、线条和状态点实测可读，投射环境、拼屏缝隙与亮度衰减纳入走查。
提供键盘可达的数据表或摘要，关键告警同时有文字和图形，不以动画轮播隐藏重要异常。

#### 表单与多步向导

只收集当前任务必要信息，字段数量不是唯一成本，理解、查找资料与纠错成本同样计入。
字段按用户认知分组并给出组标题，单列为主，输入框长度反映合理输入长度。
标签持久可见，示例和格式要求在输入前可发现，不在获得焦点时立即报错。
可自动检测的格式应容错空格、全半角和常见分隔符，自动修正必须可预测且可编辑。
即时校验在合适时机提供成功与错误反馈，服务端最终校验失败时保留全部合法输入。
向导只在步骤存在真实依赖或需要降低复杂度时使用，不为增加页面曝光拆步。
步骤条显示总步骤、当前步骤、每步名称和完成状态，允许返回修改并说明对后续步骤的影响。
开始前列出所需材料和预计成本，最后一步使用“提交申请”等结果型按钮而非笼统“下一步”。
长流程自动保存草稿、显示保存状态，会话失效和跨设备恢复有明确策略。
提交成功提供结果、编号和后续路径；异步审核要区分“已受理”与“已通过”。

#### 空态、加载、错误与权限态

首次使用空态解释价值并给一个主动作；搜索无结果显示条件、改词建议和清除筛选入口。
用户主动清空后的空态保持轻量，不再次强行营销或恢复已删除内容。
局部加载只锁定相关区域，页面骨架避免布局跳动，旧数据更新时标识刷新状态而不是整块闪白。
按钮加载保留原宽度并防止重复提交；可量化任务显示真实进度，不能伪造百分比。
长时间等待说明当前阶段，可后台运行时允许离开，可安全取消时提供取消。
字段错误靠近字段并给出修复方法，页面错误说明影响与重试，系统错误保留用户输入。
网络离线区分“无连接”“服务失败”“请求超时”，提供重试、缓存内容或稍后同步状态。
错误码用于客服诊断可附带展示，但不能以 `500`、`unknown error` 替代可理解说明。
无权限与对象不存在按安全策略区分，既不能泄露敏感对象，也要让合法用户知道如何申请权限。
权限不足页面说明所需角色、可用替代动作和申请入口，审批后返回原任务。
所有状态都提供下一步，不出现无出口空白页、永久 spinner 或只写“出错了”的死路。

#### 响应式与跨端差异

断点由内容何时拥挤、换行或失去可操作性决定，设备档位只作测试参考。
Web 可用 `0/600/840/1200/1600 CSS px` 作为内容断点评审起点，允许按组件增加局部容器查询。
Android 按实际窗口宽度区分 compact（小于 `600 dp`）、medium（`600–839 dp`）、expanded（不小于 `840 dp`）。
Material 3 大屏布局可进一步评审 large（`1200–1599 dp`）与 extra-large（不小于 `1600 dp`）的窗格策略。
iOS/iPadOS 使用 horizontal/vertical 的 compact/regular size classes，不按设备名称或横竖屏硬编码布局。
在断点前后各测试一个像素，并覆盖窗口拖拽、旋转、分屏、折叠、浏览器缩放和动态工具栏。
桌面 Web 利用宽屏并排比较、键盘效率、多窗口和适度高密度，移动 H5 优先单列、弱网与单手任务。
移动 H5 必须处理浏览器返回、地址栏伸缩、安全区、软键盘、深链和分享，不照搬原生手势。
跨端共享对象、状态、文案和权限，平台只改变呈现与交互，不制造功能规则分歧。
触摸、鼠标、键盘、屏幕阅读器和大字体分别作为独立测试维度，而非只改视口宽度截图。

### 七、设计系统、交付与验收

#### Design Token 命名与治理

Token 是设计与代码共享的具名决策，组件和设计文件不得继续散落硬编码颜色、字号、圆角与间距。
采用 reference、system、component 三层：基础值、语义角色、组件绑定逐级引用。
推荐结构为 `命名空间.层级.类别.角色.尺度或状态`，全库统一小写和分隔符。
示例：`ref.color.blue.600` 指向基础色值，`sys.color.action.primary` 指向语义角色。
示例：`comp.button.primary.container.default` 指向 `sys.color.action.primary`，不直接写十六进制。
文字色使用 `sys.color.content.primary`，表面使用 `sys.color.surface.raised`，避免以“灰色七”表达用途。
字号、行高、字重作为组合 typography token 管理，避免单独引用字号后遗漏行高。
浅色、深色、高对比、密度和 RTL 是上下文，不在业务组件中复制一套 `dark-xxx` 局部变量。
命名描述用途而非当前外观；品牌换色时名称保持稳定，值的变化有版本记录。
基础 token 不直接跨层写入复杂组件，组件 token 尽量引用 system 或 reference。
废弃 token 先标记 deprecated、给出替代与迁移期限，再通过 lint 和搜索清除引用。
设计库、前端包和移动端包使用同一命名映射，版本差异通过发布说明和自动化测试管理。

#### 组件与状态矩阵

每个组件文档包含用途、何时不用、结构、变体、状态、内容规则、响应式、无障碍和 token。
交互组件至少覆盖 default、hover、focus-visible、active、selected、disabled、loading、error 的适用状态。
状态不是每组件机械全选，应在矩阵中标注“不适用”及原因，避免遗漏组合状态。
hover 与 selected 不得混淆，focus-visible 不能只改变极浅色背景，disabled 与只读语义分开。
loading 保留布局与操作上下文，异步失败返回可恢复状态，避免永久禁用。
同一组件的 primary、secondary、text、danger 变体分别验证对比度与状态差异。
组件需覆盖空内容、超长内容、极大数字、多语言、RTL、大字体、键盘和屏幕阅读器。
优先组合现有组件，只有出现重复任务需求且无法由现有变体解决时才新增组件。
组件变更先评估所有使用场景，以视觉回归、交互测试和无障碍检查作为发布门禁。

#### 标注、走查与交付物

交付包含任务流、页面清单、关键原型、真实文案、状态矩阵、响应式规则和权限说明。
设计稿命名对应路由、对象与状态，不使用“最终版2”“最新版改”等无法追踪的名称。
标注引用 token 与组件属性，不重复手抄整页像素值；特殊尺寸必须说明原因和适配规则。
切图提供适当格式、尺寸、语义与主题版本，图标不将文字无必要地栅格化。
开发联调前确认接口空态、分页、超时、失败、缓存和字段极值，避免只实现 happy path。
设计走查在真实构建上进行，覆盖设计还原、任务逻辑、内容、交互、性能感知与无障碍。
问题按 P0 阻断或合规、P1 严重任务受损、P2 明显体验问题、P3 优化建议分级并指定责任人。
走查结论记录环境、复现步骤、预期、实际、截图或录像和修复版本，不只写“样式不对”。
上线后通过核心任务漏斗、错误日志、客服反馈和可用性复测闭环验证设计结果。

#### 可用性测试与验收标准

形成性测试每轮邀请五至八名覆盖关键角色与经验水平的用户，用于发现问题，不宣称统计代表性。
测试任务来自真实目标，提供情境而非操作答案，记录成功、耗时、错误、回退、求助和观察笔记。
任务成功必须有客观标准，不能把“用户最终点到页面”都算作成功。
计时从用户理解任务后开始，剔除无效中断需有预先规则，同时报告中位数与分布。
SUS 使用十题交替正负向量表，换算为 `0–100` 分；它不是百分比，也不应脱离任务表现单独解释。
核心任务发布基线：任务成功率不低于 `90%`，中位耗时不劣于既定基线，且无未解决的阻断错误。
新产品或核心流程改版以 `SUS ≥ 80` 且不低于上版为项目目标；若未达标，必须复测主要问题修复。
涉及无障碍的核心任务须由相关辅助技术用户参与，不能仅用无障人士模拟代替。
可用性验收与 WCAG 2.2 AA 检查、设计走查共同通过后才可发布，严重问题不得以排期为由豁免。
样本不足以支持统计结论时使用定性证据和分轮迭代，重大定量比较另行设计样本量与对照。

#### 现行标准基线与更新

无障碍以 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) AA 为基线，细项以对应 Success Criterion 原文为准。
iOS/iPadOS 以 [Apple Human Interface Guidelines：Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) 和 Layout 为平台基线。
Android 与跨端 Material 组件参考 [Material Design 3：Design tokens](https://m3.material.io/foundations/design-tokens/overview)。
Android 响应式以 [Window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/window-size-classes) 描述的实际窗口为准。
WCAG 文本、非文本对比度和目标尺寸分别见 [1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)、[2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。
平台文档更新时由设计系统负责人评审影响，形成变更记录、迁移规则和验证结果，不得静默替换既有规则。

### 八、界面上线前设计走查清单（30 条）

1. 核心用户、情境、目标与成功标准明确，页面主动作与之一致。
2. 对象命名、分类、导航和返回路径符合用户心智，未照搬内部组织结构。
3. 首屏五秒内能识别页面用途、当前位置、首要信息和下一步。
4. 核心流程不存在死路，深链、返回、刷新和重新登录后的去向正确。
5. 高频操作热区达到 `44 pt/48 dp` 基线，Web 同时满足 WCAG 最低目标尺寸要求。
6. 主操作与危险操作距离、样式、文案和确认方式不会诱发误触。
7. 单手、左右手、横竖屏、安全区和软键盘场景均可完成核心任务。
8. 普通文字对比度至少 `4.5:1`，大号文字和必要非文本信息至少 `3:1`。
9. 颜色不是表达错误、成功、选中、等级或图表差异的唯一手段。
10. 正文放大 `200%`、系统大字体和翻译变长后不裁切、不重叠、不丢功能。
11. 键盘可完成所有核心任务，焦点可见、顺序合理、无遮挡、无键盘陷阱。
12. 控件具有正确名称、角色、状态和值，图片、图标按钮和表单标签可被辅助技术理解。
13. 减少动态效果设置生效，无高频闪烁、不可关闭的自动轮播或干扰性动画。
14. 栅格、字阶、间距、圆角、图标和插画风格统一，未出现无依据的局部例外。
15. 长文行宽、行高、字重和中西文混排可读，数字表格对齐与小数位统一。
16. 浅色、深色和高对比主题分别走查，未使用简单反色代替深色设计。
17. 所有选择、默认值和推荐项可解释，无默认营销订阅、附加商品或非必要授权。
18. 价格、费用、续费、库存、稀缺和评价真实透明，无暗黑模式与诱导性文案。
19. 表格筛选、排序、分页、列设置和批量选择范围清晰，返回后上下文按需求保留。
20. 批量或不可逆操作显示影响对象与数量，并具备撤销、恢复或适当确认。
21. 表单标签持久可见，必填、示例和格式明确，校验时机适当且错误可修复。
22. 多步向导显示总步骤与当前进度，可返回修改、自动保存并清楚区分受理与完成。
23. 首次空态、无结果、清空、局部加载、长等待和离线路径均有合适反馈与下一步。
24. 错误说明发生了什么、影响什么、如何恢复，输入内容不会因失败被清空。
25. 无权限、对象不存在、登录过期和审批中状态符合安全策略且提供合法解决路径。
26. 加载与提交具备防重复机制，乐观更新失败可回滚，支付等操作不提前显示成功。
27. 断点前后、分屏、窗口缩放、动态工具栏和极值内容下无失控布局或双向滚动。
28. 桌面与移动端规则一致但交互适配平台，hover、拖拽和手势均有等价入口。
29. 设计稿、token、组件、真实文案和开发实现一致，P0/P1 走查问题已全部关闭。
30. 核心任务成功率、耗时、SUS 及 WCAG 2.2 AA 验收达到项目门槛，并保留复测记录。
